## Language & runtime

TypeScript ~5.7, Node 22 or 24, Yarn 4.18.1 workspaces (`packages/*`, `plugins/*`). ESM-style `import`
syntax in `.ts`/`.tsx` source, compiled by `@backstage/cli`. Knex migrations are plain CommonJS `.js`
with `// @ts-check` and JSDoc types. Type checking runs once from the repo root (`yarn tsc`). Prettier
config comes from `@backstage/cli/config/prettier` (single quotes, trailing commas, 2-space indent,
arrow parens avoided for single params: `table => {}`).

Every new `.ts/.tsx/.js/.jsx` file needs the Apache 2.0 header with the current year (2026). Existing
files keep their original year.

## Framework

Backstage (in-repo; this IS the framework). Two frontend systems exist side by side:
- old: `@backstage/core-plugin-api` (`createRouteRef`, `useRouteRef`, `createPlugin`) — `plugins/*/src/plugin.ts`, `routes.ts`, `components/`
- new: `@backstage/frontend-plugin-api` (`PageBlueprint`, `EntityContentBlueprint`, `createFrontendPlugin`) — `plugins/*/src/alpha/`
Backend: `@backstage/backend-plugin-api` (`createBackendPlugin`, `coreServices.*`), Express routers built on a
generated OpenAPI router (`@backstage/backend-openapi-utils`), knex for the database.
UI: `@backstage/ui` (BUI) components (`Alert`, `Button`) in newer code; Material UI v4 still present in older code.

## Conventions detected

### File naming
- One component per folder, PascalCase, with barrel: `plugins/catalog/src/components/EntityOrphanWarning/{EntityOrphanWarning.tsx, EntityOrphanWarning.test.tsx, index.ts}`
- Backend classes PascalCase per file with co-located test: `plugins/catalog-backend/src/service/DefaultRefreshService.ts` + `.test.ts`
- Function modules camelCase: `createRouter.ts`, `useExternalRedirect.ts`, `handleMetaRedirects.tsx`
- Migrations: `plugins/catalog-backend/migrations/YYYYMMDDHHMMSS_snake_case.js` (latest `20261007000000_stitch_failure_count.js`)
- catalog-model policies: `packages/catalog-model/src/entity/policies/<Name>EntityPolicy.ts` + `.test.ts`

### Handler / controller shape
Routes are chained on an OpenAPI-validated router in `plugins/catalog-backend/src/service/createRouter.ts`;
each wraps work in an auditor event:

```ts
    .get('/entities/by-name/:kind/:namespace/:name', async (req, res) => {
      const { kind, namespace, name } = req.params;
      const entityRef = stringifyEntityRef({ kind, namespace, name });

      const auditorEvent = await auditor.createEvent({
        eventId: 'entity-fetch',
        request: req,
        meta: { queryType: 'by-name', entityRef: entityRef },
      });

      try {
        const { items } = await entitiesCatalog.entitiesBatch({
          entityRefs: [stringifyEntityRef({ kind, namespace, name })],
          credentials: await httpAuth.credentials(req),
        });
        await auditorEvent?.success();
        writeSingleEntityResponse(res, items, `No entity named '${name}' found, ...`);
      } catch (err) {
        await auditorEvent?.fail({ error: err });
        throw err;
      }
    })
```

New/changed endpoints must also be declared in `plugins/catalog-backend/src/schema/openapi.yaml`, then
regenerated with `yarn --cwd plugins/catalog-backend generate`, which rewrites
`plugins/catalog-backend/src/schema/openapi/generated/**` and `packages/catalog-client/src/schema/openapi/generated/**`
(files headed `THIS IS AN AUTOGENERATED FILE. DO NOT EDIT THIS FILE DIRECTLY.`).

### Service shape
Interfaces in `types.ts`, `Default*` implementations, `Authorized*` decorators that wrap them with
permission checks (`AuthorizedEntitiesCatalog` wraps `DefaultEntitiesCatalog`). Constructor takes a single
options object. Errors from `@backstage/errors` (`InputError`, `NotFoundError`, `ConflictError`).

### Config
`app-config.yaml` read through `@backstage/config` (`config.getOptionalBoolean('catalog.xxx')`); new
config keys must be declared in the package's `config.d.ts` (e.g. `plugins/catalog-backend/config.d.ts`)
with TSDoc. Request validation uses `zod/v3` in the router.

### Data layer
knex, schema changes only via new migration files (never edit old ones):

```js

exports.up = async function up(knex) {
  await knex.schema.alterTable('stitch_queue', table => {
    table.integer('failure_count').notNullable().defaultTo(0);
  });

/** @param {import('knex').Knex} knex */
exports.down = async function down(knex) {
  await knex.schema.alterTable('stitch_queue', table => {
    table.dropColumn('failure_count');
  });

```

Row types live in `plugins/catalog-backend/src/database/tables.ts`. `plugins/catalog-backend/CLAUDE.md`
asks for the `/catalog-db-performance` battery before and after query/index/schema changes, and
`report.sql.md` is regenerated by `yarn build:api-reports`.

### Entity model
Entity shape is defined in TypeScript (`packages/catalog-model/src/entity/Entity.ts`) AND JSON schema
(`packages/catalog-model/src/schema/EntityMeta.schema.json`); a new `metadata` field needs both, plus
validation (`FieldFormatEntityPolicy`). Well-known annotations are `ANNOTATION_*` constants with TSDoc
and `@public` in `packages/catalog-model/src/entity/constants.ts`.

## Notes for downstream codegen
- Match each package's own style; packages differ. Consistency within a package wins.
- New source files: Apache 2.0 header with 2026. Never touch the year on existing files.
- Never hand-edit `**/schema/openapi/generated/**`; edit `openapi.yaml` and regenerate.
- Public API changes require `yarn build:api-reports` (updates `report*.api.md`) and a changeset in
  `.changeset/` (written by hand, never via the changeset CLI). Packages below 1.0.0: breaking => minor,
  new feature => patch; at or above 1.0.0: breaking => major, new feature => minor. Changeset text is
  adopter-facing, no internal symbol names.
- Behavior changes need docs (TSDoc, package README, or `/docs/features/software-catalog`, `/docs/features/techdocs`)
  following `/docs/contribute/doc-style-guide.md`.
- Do not run `yarn build`, `yarn release`, or `changeset version`. Never edit ESLint/Prettier/TS config or `docs/releases/**`.
- Entity-page changes must cover both the old (`components/`, `plugin.ts`) and new (`alpha/`) frontend systems.
