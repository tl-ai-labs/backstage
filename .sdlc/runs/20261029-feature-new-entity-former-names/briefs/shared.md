## Conventions

- Every new .ts or .tsx source file starts with the Apache 2.0 header reading 'Copyright 2026 The Backstage Authors', copied from the style file; existing headers keep their year.
- Formatting is Prettier with the repo config (single quotes, trailing commas, 2-space indent, 80 columns); markdown and YAML are formatted by Prettier as well.
- Match the existing style of each file and package: import grouping, named exports, arrow vs function declarations, and error handling as the neighbouring code does it.
- Every new public export carries TSDoc with a release tag (@public) as the surrounding exports do; internal helpers carry no release tag.
- Entity refs are built and parsed only with stringifyEntityRef, parseEntityRef and entityRouteParams; never concatenate kind, namespace and name by hand.
- User-facing frontend strings come from the plugin translation ref (catalogTranslationRef in plugins/catalog, techdocsTranslationRef in plugins/techdocs); no string literals in JSX or alert messages.
- Tests use Jest; prefer fewer thorough tests with several assertions; React tests use @testing-library/react screen and findBy\* queries, never add test IDs to implementation code.
- Backend database tests use TestDatabases.create() with describe.each or it.each over databases.eachSupportedId() and applyDatabaseMigrations, as the existing test in the same file does.
- Hand-edited OpenAPI generated files keep their AUTOGENERATED banner and mirror the shape and formatting of the neighbouring generated entries exactly, as the generator would emit them.
- Documentation follows docs/contribute/doc-style-guide.md: present tense, active voice, address the reader as you, code style for annotation names, paths and endpoints, and list items that are sentences end with a period.
- Changesets are new files in .changeset/ with YAML front matter naming the package and bump, followed by an adopter-facing paragraph that names no internal symbols beyond public API.
- No new runtime or dev dependencies are added to any package.json.

## Decisions

- How an entity declares former names: The annotation backstage.io/former-names (constant ANNOTATION_FORMER_NAMES), a comma-separated list of entity refs; short forms default kind and namespace to the declaring entity's own. (not a new metadata.formerNames field) — Approved at Gate 1; an annotation needs no metadata schema change and matches other opt-in catalog behaviour.
- Parser vs validator in catalog-model: parseFormerEntityRefs(entity) is lenient (never throws, silently drops unparseable items, items of another kind and the entity's own ref, lowercases and de-duplicates); validateFormerEntityRefs(entity, validators) throws an Error naming the first bad item and is called from FieldFormatEntityPolicy. (not a separate public FormerNamesEntityPolicy class wired into CatalogBuilder; not a parser that throws) — FieldFormatEntityPolicy is already in the default policy chain, so a bad item becomes a processing error with no new wiring; the backend and the in-memory client need a parser that cannot crash stitching or lookups when custom policies replace the defaults.
- Index storage for former refs: buildEntitySearch emits one search row per former ref with key 'former_entity_ref' (exported as FORMER_ENTITY_REF_SEARCH_KEY) and value the lowercased full ref; 'former_entity_ref' is also added to SPECIAL_KEYS so a raw entity field of that name is never indexed under it. The lookup is an exact (key, value) match served by the existing search_key_value_entity_idx index. (not a new former_entity_refs table with a Knex migration; not a LIKE match on the metadata.annotations.backstage.io/former-names search row) — The existing (key, value, entity_id) index serves an exact match with no migration (NFR-2, requirements out-of-scope item 6), and syncSearchRows already adds and removes rows when the annotation changes.
- Backend resolution contract: EntitiesCatalog gains resolveFormerEntityRef(request: { formerRef: string; credentials: BackstageCredentials }): Promise<FormerEntityRefResolution>, where FormerEntityRefResolution is { type: 'current' } | { type: 'none' } | { type: 'conflict'; entityRefs: string[] } | { type: 'resolved'; entityRef: string }. The method is required on the interface and every test mock of EntitiesCatalog adds it. (not an optional interface method; not resolving inside the router with raw knex) — Keeps SQL in DefaultEntitiesCatalog and permissions in AuthorizedEntitiesCatalog, the same split every other lookup uses.
- Permission evaluation: DefaultEntitiesCatalog resolves over all entities (so a hidden claimant still counts for hijack and conflict detection); AuthorizedEntitiesCatalog then checks the single ref it would reveal ('current' -> the requested ref, 'resolved' -> the claimant) through its own entitiesBatch with the caller's credentials, and returns { type: 'none' } when that entity is not readable. 'conflict' and 'none' pass through unchanged. (not filtering claimants by permission before counting them) — FR-6 requires the entitiesBatch permission path, and NFR-5 requires an unreadable entity to be indistinguishable from no entity.
- HTTP responses of GET /entities/by-former-name/:kind/:namespace/:name: resolved -> 200 with { entityRef }; current -> 404 NotFoundError "The entity ref '<ref>' is the current ref of an entity, not a former one"; none and conflict -> 404 NotFoundError "No entity has the former name '<name>', with kind '<kind>' in namespace '<namespace>'"; conflict additionally logs logger.warn naming all claimant refs, never in the response. (not a 409 for conflicts; not naming claimants in the 404 body) — Gate 1 chose no redirect plus a warning for conflicts; identical bodies for none, unreadable and conflict leak nothing.
- OpenAPI contract and generated code: operationId GetEntityRefByFormerName, tag Entity, path parameters kind/namespace/name by $ref, responses 200 (schema $ref FormerEntityRefResponse), 400 and default ErrorResponse, security like by-name. New component schema FormerEntityRefResponse: object, required [entityRef], entityRef string, additionalProperties false. The generated server and client files are edited by hand to exactly what the generator emits; no generator tooling unit. (not running backstage-repo-tools package schema openapi generate as a tooling unit) — The generator empties and rewrites whole directories in two packages, which a single tooling path cannot record; the project check 'openapi-validate' proves router.ts still deep-equals openapi.yaml.
- Client method: CatalogApi gets optional getEntityRefByFormerRef?(formerRef: string | CompoundEntityRef, options?: CatalogRequestOptions): Promise<string | undefined>; CatalogClient calls DefaultApiClient.getEntityRefByFormerName and returns body.entityRef, undefined on 404; InMemoryCatalogClient applies the same rules without permissions using parseFormerEntityRefs. — FR-9 and FR-10; optional so third-party CatalogApi implementations still compile.
- Rename marker and notice on the catalog entity page: The redirect lives in the shared hook useEntityFromUrl (used by both the old CatalogEntityPage and the alpha CatalogEntityPage). It appends the search param renamedFrom=<old full ref>, keeps the sub-route from useParams()['*'], the other search params and the hash. When an entity loads with renamedFrom present, the hook posts one alertApi message (severity 'info', default dismissible display) with t('entityPage.renamedNotice', { formerRef }) and then removes the param with a replace navigation. (not an inline banner component inside each of the three entity layouts) — One code path covers both frontend systems; the app-level alert display is already dismissible, and the old Page grid has no free slot for an inline banner.
- Rename redirect and notice in TechDocs: useExternalRedirect, which already fetches the entity once per docs entity, calls catalogApi.getEntityRefByFormerRef only when getEntityByRef returned undefined, and navigates with replace to the docs route of the current ref plus the docs sub-path, the search params with renamedFrom=<old full ref>, and the hash. A new TechDocsRenamedNotice renders TechDocsRedirectNotification (given a new optional actionLabel prop) when renamedFrom is present; TechDocsReaderPage renders it, which covers the alpha reader because TechDocsReaderRouter renders the same TechDocsReaderPage. (not a second hook with its own entity fetch; not a new Snackbar component) — No extra request on a normal docs load and FR-15 asks to reuse the existing redirect-notification pattern.
- Changeset bumps: minor for @backstage/catalog-model, @backstage/catalog-client, @backstage/plugin-catalog-backend, @backstage/plugin-catalog and @backstage/plugin-techdocs, one changeset file per package. — Approved at Gate 1; each package needs its own adopter-facing message.
