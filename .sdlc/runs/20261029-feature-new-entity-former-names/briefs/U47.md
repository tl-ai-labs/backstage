### U43 — edit `docs/features/software-catalog/well-known-annotations.md` (docs)

Behaviour: Documents backstage.io/former-names: format, claim rules, conflict behaviour and permissions.

Rules:

1. 1. Section heading '### backstage.io/former-names' followed by a YAML example: metadata.name new-service with annotation backstage.io/former-names: 'old-service, legacy/older-service'.
2. 2. Format: a comma-separated list of entity refs; whitespace around items is ignored; a short form (name or namespace/name) takes the entity's own kind and namespace; refs are compared case-insensitively.
3. 3. Claim rules as a list: a former ref must have the same kind as the entity; it must not be the entity's own current ref; it must follow the usual naming rules; a ref in another namespace is allowed. An invalid item is reported as a processing error on the entity that names the item.
4. 4. Behaviour: opening the entity page or TechDocs URL of a former ref redirects to the entity's current URL and shows a notice that the entity was renamed. A live entity always keeps its own name, so if an entity currently holds the ref there is no redirect. If more than one entity claims the same former ref, there is no redirect and the catalog logs a warning.
5. 5. Permissions: the redirect only happens when the user may read the entity that claims the ref; otherwise the page shows Entity not found, the same as when nothing claims the ref.
6. 6. Mention the catalog endpoint GET /entities/by-former-name/<kind>/<namespace>/<name> with a link to api.md.
