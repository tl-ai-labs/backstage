# Security Review — pass1 (brownfield, feature-new: entity former names)

Scope: the 52 files in `provenance.json` (`git_head_before` cb8b07905b). Edited files were reviewed as diffs against that commit, and new files were read in full. Generated OpenAPI files were checked only for how they encode paths and handle auth headers.

## Summary

The new `GET /entities/by-former-name/:kind/:namespace/:name` route follows the same pattern as the existing `by-name` route. It goes through the same router, so `httpAuth` and the plugin auth policy apply. The audit event is created before the lookup. The DB queries use knex bindings. `AuthorizedEntitiesCatalog` returns the same 404 when the caller may not read the claimant or the live entity that holds the ref, so callers cannot use the response to learn about entities they may not read. Frontend redirects stay inside the app, because they are built from route refs with encoded params. No secrets, credentials or dependency changes were introduced. There is one Medium finding: any entity author can claim a former ref in any namespace, which lets them take over old links or block a real redirect. There are also two Low findings.

## Passing checks

- Route guard: the new route is on the same authenticated router as `by-name`, uses `httpAuth.credentials(req)`, and the OpenAPI `security` block matches `by-name`.
- Authz: `resolved` and `current` results are checked against `catalogEntityReadPermission` (deny and conditional) through `entitiesBatch`. If the caller is denied, the result is `none` and the client gets the same 404.
- Audit: `auditor.createEvent` runs before the lookup and records the former ref. `success` records `currentEntityRef`, and `fail` runs on every 404. `audit-events.md` documents the new queryType.
- Injection: the knex queries use bindings. The generated client expands the path with a URI template, so path segments are encoded.
- Open redirect: catalog redirects use `entityRoute(entityRouteParams(ref, { encodeParams: true }))`. TechDocs redirects use the `rootDocsRouteRef` function with a ref returned by the server and checked by the naming validators. Both stay inside the app.
- Error responses: `NotFoundError` messages repeat only the requested ref, the same as `by-name`.
- Secrets: no hardcoded secrets in touched source. `CatalogClient.test.ts:30` `'fake-token'` is a placeholder already present before this run. The docs and changesets contain no credentials.
- Test fixtures (`formerNames.test.ts`, `CatalogEntityPage.test.tsx`, others): no real credentials.
- PII encryption or masking, JWT secret, password hashing, audit table append-only, helmet, rate limiting, `.env` handling: n/a, not in the touched set.
- Dependencies: no manifest or lockfile was touched, so there is no change and `npm audit` was not re-run.

## Required fixes before sign-off

- Medium: limit `backstage.io/former-names` claims to the entity's own namespace, or put cross-namespace claims behind config (`packages/catalog-model/src/entity/formerNames.ts`).
- Low findings are advisory and do not block, but are recommended: pass `renamedFrom` through navigation state instead of the query string.

## Noted (pre-existing, out of scope)

- The catalog backend has no rate limiting on read endpoints. The new endpoint adds two indexed queries per not-found lookup, the same cost as existing lookups.
