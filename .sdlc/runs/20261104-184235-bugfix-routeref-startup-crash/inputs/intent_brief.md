# Intent Brief — bugfix — app root elements crash on useRouteRef during startup

## Context

Seed (the user's words): In the new frontend system, app root elements that call useRouteRef during startup crash with "No path for routeRef".

Interview answers (the user's words, verbatim):

> Observed: in the new frontend system, app root elements (components rendered around the whole app, such as a global announcement banner) render between sign-in and app finalization, before page routes are known. A root element that calls useRouteRef for a page route throws "No path for routeRef", and the app shows an extension error box in place of the banner. Reported in backstage/backstage#35932.
>
> Expected: the banner renders, and useRouteRef returns the correct link once the app is finalized, without render loops.
>
> Files involved: packages/frontend-app-api (prepareSpecializedApp, phaseApis) and packages/frontend-plugin-api (useRouteRef, possibly a lifecycle API), plus tests and docs.
>
> How we know it's fixed: a createSpecializedApp test renders a root element that calls useRouteRef before and after finalization and asserts the link resolves; the test fails before the fix; tsc, lint and API reports pass.

What the branch's code shows (read from this branch only; no upstream fix consulted):

- `packages/frontend-app-api/src/wiring/treeLifecycle.tsx` (`createBootstrapApp`) instantiates the bootstrap tree with `stopAtAttachment` at `app/root.children`, so page extensions behind that boundary have no instances during bootstrap. `clearFinalizationBoundaryInstances` deliberately keeps the bootstrap instances of `app/root.elements`.
- `packages/frontend-app-api/src/wiring/phaseApis.tsx` (`RouteResolutionApiProxy`, `instantiateAndInitializePhaseTree`): one proxy object serves both phases. It is initialized at bootstrap with route info extracted from the partial tree (`extractRouteInfoFromAppNode` reads only instantiated nodes), so no page route paths are known, and re-initialized at finalization (`prepareSpecializedApp.tsx`, `finalizeFromSessionState`) without changing its identity.
- `packages/frontend-plugin-api/src/routing/useRouteRef.tsx` memoizes the resolved route function on `[routeResolutionApi, routeRef, pathname]`, so a root element that resolved `undefined` during bootstrap is not recomputed when finalization swaps the proxy's delegate.
- The exact text "No path for routeRef{…}" is thrown by the old-system hook in `packages/core-plugin-api/src/routing/useRouteRef.tsx` when a non-optional ref resolves to `undefined`; the new-system hook returns `undefined` instead. `core-plugin-api` is outside this brief's scope.
- `packages/core-compat-api/src/compatWrapper/ForwardsCompatProvider.tsx` (`CompatRouteResolutionApi`) also implements `RouteResolutionApi` and is outside scope, so a new required member on that interface would break `yarn tsc`.

## Goal

App root elements that call `useRouteRef` for a page route render without an extension error during startup (between sign-in and finalization), and once the app is finalized `useRouteRef` returns the correct link for that route, without render loops.

## Acceptance criteria

1. A new test in `packages/frontend-app-api/src/wiring/createSpecializedApp.test.tsx` uses `prepareSpecializedApp` with a root element (`app/root.elements`) that calls `useRouteRef` for a page route mounted behind `app/root.children`. It renders the root element before and after finalization and asserts that it renders without an error and that the link resolves to the page's path once the app is finalized. The test switches from the bootstrap element to the finalized element inside one React root (as `PreparedAppRoot` in `packages/frontend-defaults/src/createApp.tsx` does), not with two separate `render` calls: a second `render` remounts the root element and would hide a stale link.
2. That test fails on the unchanged branch and passes after the fix.
3. No render loop: the root element re-renders a bounded number of times across finalization.
4. Test command passes (the BS-BF-08 study's fixed command, used word for word): `CI=true yarn test packages/frontend-app-api packages/frontend-plugin-api && yarn tsc && yarn lint:all && yarn build:api-reports`.
5. Changesets cover each changed published package with the correct bump, and docs describe any new or changed behavior or API.
