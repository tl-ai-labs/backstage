## Conventions

- Every new .ts/.tsx file starts with the Apache-2.0 block header exactly as in plugins/notifications/src/plugin.ts, with the line 'Copyright 2026 The Backstage Authors'. Never change the year on an existing file.
- Formatting is Prettier with the repo config (@backstage/cli/config/prettier): 2-space indent, single quotes, trailing commas, semicolons, 80-column wrap, arrow functions with a single parameter written without parentheses (x => x).
- Named exports only (ADR003); the only default export stays the existing createFrontendPlugin export in plugins/notifications/src/alpha.tsx. Function components take a typed props parameter; never React.FC (ADR006). No default React import: import hooks and types by name from 'react'.
- Per-module imports for utility libraries, as the package already does: import throttle from 'lodash/throttle'; import useAsyncRetry from 'react-use/esm/useAsyncRetry'.
- UI in plugins/notifications uses @backstage/ui (Flex, Text, ButtonIcon), @backstage/core-components (Link, Progress, ResponseErrorPanel) and @remixicon/react icons; styling goes in the component's existing CSS module, never inline style objects.
- Every user-visible string in plugins/notifications comes from notificationsTranslationRef through const { t } = useTranslationRef(notificationsTranslationRef), with useTranslationRef imported from '@backstage/core-plugin-api/alpha' and the ref from the relative 'translation' module.
- Every symbol newly exported from a package entry point (src/index.ts, src/alpha.tsx) has a TSDoc comment with a release tag (@public, or @alpha in alpha.tsx). report\*.api.md files are only written by the API report tooling, never typed.
- Tests run on Jest through backstage-cli (CI=1 yarn test <path>). In plugins/notifications use React Testing Library (screen, findBy*, fireEvent from '@testing-library/react'), renderInTestApp and TestApiProvider from '@backstage/test-utils', and jest-dom matchers (already loaded by src/setupTests.ts). Prefer findBy* and waitForElementToBeRemoved over waitFor. Add no test IDs to implementation code. Prefer a few thorough tests with several assertions each.
- Mock APIs in tests are plain objects of jest.fn() cast to the API type (for example { getNotifications: jest.fn(), ... } as unknown as NotificationsApi), passed through TestApiProvider apis={[[notificationsApiRef, api], [toastApiRef, toastApi]]}; toastApiRef comes from '@backstage/frontend-plugin-api' and signalApiRef from '@backstage/plugin-signals-react'.
- Notification fixtures in tests are full Notification objects from '@backstage/plugin-notifications-common': { id, user: 'user:default/guest', created: new Date(...), origin: 'test', payload: { title, severity: 'normal' } }.
- Documentation follows docs/contribute/doc-style-guide.md: U.S. English, second person, present tense, sentence-case headings, code style for package names, paths and props, fenced code blocks tagged with a language (tsx, yaml).
- Changesets are hand-written markdown files in .changeset/ with front matter of the form '<package name in single quotes>': patch, then one short paragraph for adopters that names no internal function, class or variable.

## Decisions

- Public names of the card: The old-system card extension is the public export UnreadNotificationsCard (plugins/notifications/src/plugin.ts, re-exported from src/index.ts); its props type UnreadNotificationsCardProps = { limit?: number; pollingIntervalMs?: number } is public; the rendered component UnreadNotificationsCardContent stays internal to the package (exported from its folder only, not from src/index.ts or src/components/index.ts). (not NotificationsHomePageCard as the extension name; not exporting the content component from the package entry) — Matches the folder name the brief names, and keeps the public API to the extension and its props, like the other home cards.
- Card defaults: limit defaults to 5 and pollingIntervalMs to 60000, both through prop destructuring defaults in UnreadNotificationsCardContent; no exported constants. — Defaults approved at Gate 1; both overridable through props.
- Where live refresh lives: Inside UnreadNotificationsCardContent, no new hook file: a refresh boolean state, a lodash throttle(setRefresh, 2000) for signals (leading edge, same as NotificationsPage), an effect that calls retry() and resets refresh when refresh is true and loading is false, a setInterval effect only when isSignalsAvailable is false, and an unmount cleanup that cancels the throttle. (not a new useUnreadNotifications hook in src/hooks; not polling through useInterval from react-use) — Single consumer; the throttle-plus-refresh-flag pattern is the one NotificationsPage already uses, and it gives at most one request per signal burst or tick (NFR-4).
- Mark-as-read list update: The card keeps the shown items in local state, replaced from each fetch result; a successful updateNotifications({ ids: [id], read: true }) filters that id out of local state without refetching; a failure leaves the item and posts toastApi.post({ title: t('unreadNotificationsCard.errors.markAsReadFailed'), status: 'danger' }). (not refetching after each mark-as-read; not an inline error message in the card) — Removal is immediate; the next signal or poll fills the list. The toast mirrors how NotificationsTable reports failed bulk actions.
- Deep-link href and route fallback: The card resolves the page root with useRouteRef(rootRouteRef)() inside a try block (the hook throws after its own hooks when the route is not mounted) and falls back to '/notifications'; item links are `${root}?id=${encodeURIComponent(notification.id)}`, the View all link is the root. (not hard-coding '/notifications'; not making rootRouteRef optional) — FR-3: use the plugin route, still render in tests and apps without the page; the hook count is the same on every render.
- Deep link on the notifications page: NotificationsPage reads id with useSearchParams from 'react-router-dom'. When the current page result is loaded and does not contain that id, it fetches getNotification(id) (a rejection resolves to undefined) and passes [pinned, ...pageNotifications] to the table; the table gets highlightedNotificationId and marks the matching row's content Flex with aria-current="true" and the CSS module class highlighted. (not switching the filters to all; not fetching by id even when the item is already on the page; not aria-selected on the table row (material-table does not expose row attributes)) — Placement approved at Gate 1 (pin at the top, keep filters). The table keeps its page size, so while a pinned row is shown it is the first of pageSize visible rows; clearing ?id restores the plain page.
- New frontend system widget: alpha.tsx adds HomePageWidgetBlueprint.make({ name: 'unread-notifications', params: { name: 'UnreadNotificationsCard', title, description, layout, components } }), extension id home-page-widget:notifications/unread-notifications, using the card defaults; no configSchema. (not makeWithOverrides with a zod configSchema for limit and pollingIntervalMs) — A config schema needs zod as a new runtime dependency of the notifications plugin, which NFR-5 forbids; the docs state the new-system widget uses the defaults.
- Card title and description strings: The extension metadata uses the literal strings title 'Unread notifications' and description 'Shows your latest unread notifications and lets you mark them as read.', identical in plugin.ts and alpha.tsx, and layout { width: { minColumns: 3 }, height: { minRows: 4 } }. Strings rendered by the card itself all come from the translation ref. (not translation keys for the extension title and description) — Extension metadata is built outside React where no translation function exists; plugins/home and plugins/search use literal titles the same way.
- New translation keys: One new block in notificationsTranslationRef messages, after sidebar: unreadNotificationsCard: { emptyMessage: 'No unread notifications', viewAll: 'View all notifications', markAsRead: 'Mark as read', errors: { markAsReadFailed: 'Failed to mark notification as read' } }. — FR-19; keys grouped by component like the existing table, sidebar and settings blocks.
- CardExtension without app context: plugins/home-react/src/extensions.tsx gets a module-private hook useProgressComponent() that returns useApp().getComponents().Progress inside a try block and the core-components Progress (imported as DefaultProgress) when useApp throws; CardExtension calls it where it called useApp. Translation still uses useTranslationRef unchanged. (not useContext checks on the versioned app context; not a CardExtension prop for the progress component) — FR-18: one unconditional hook call, same behavior inside an app, default progress otherwise; no new public API.
- home-react test harness: plugins/home-react/src/extensions.test.tsx renders with createRoot from 'react-dom/client' and act from 'react', sets globalThis.IS_REACT_ACT_ENVIRONMENT = true, and replaces useTranslationRef through jest.mock('@backstage/frontend-plugin-api', ...) with jest.requireActual spread so the card renders with no API or app context; assertions use container.textContent and querySelector('[role="progressbar"]'). (not @testing-library/react and @backstage/test-utils (not dependencies of plugins/home-react, and its package.json is outside the change)) — NFR-5: the home-react test uses only that package's existing dependencies.
- API reports: Two tooling steps regenerate plugins/notifications/report.api.md (yarn build:api-reports plugins/notifications, which runs tsc first) and then plugins/notifications/report-alpha.api.md (yarn build:api-reports:only plugins/notifications, reusing the type output of the first step). plugins/home-react/report.api.md is not regenerated: CardExtension is not exported from any home-react entry point, so its public API does not change. — NFR-7: reports come from the tool; each written report is recorded by its own step.
