## Decisions

- How cross-step `dependencies` resolve: Rewrite the active step's schema just before it reaches rjsf: every top-level `dependencies` entry whose key is an earlier-step field moves to a top-level `allOf` entry of `if`/`then` guarded by `required: [key]`. The logic lives in `lib/crossStepConditions.ts`. (not Inject earlier-step properties into later schemas as hidden fields, as #35196 does; not Add earlier-step properties to `useTemplateSchema` output; not Resolve the conditions by hand and render a flattened schema) — `processDependencies` in @rjsf/utils 5.24.13 skips a dependency whose key is not in the step's `properties`, and that is the only cause of the bug. The rewrite means the same thing in JSON Schema and adds no property, whereas injection breaks `ui:order` (`orderProperties` throws on an unlisted property), exposes earlier fields to custom layouts and validates them in the later step (FR-4).
- Where the rewrite is applied: Only at `Stepper`'s `schema` prop on `Form`. `steps[n].schema` and `steps[n].mergedSchema` stay as `useTemplateSchema` returns them. (not Rewrite inside `useTemplateSchema`) — `useTemplateSchema` is a public alpha hook and its existing test pins `second.schema` to `{ dependencies }`. Review and the async validators read `mergedSchema` through json-schema-library, which already resolves a dependency without its key in `properties`.
- What counts as an earlier-step field: A key defined by a step before this one (its `properties`, top-level `allOf` entries' `properties`, or any conditional branch) and defined nowhere in this step, over the feature-flag-filtered `steps`, read from each step's `.schema`. (not Count a key defined in both steps as earlier-step) — The requirements define a same-step condition as one reading fields of its own step, so a key the step defines itself stays with today's rjsf path (FR-7). Branch-defined keys count so chained conditions work.
- Drop rule: `omitHiddenCrossStepValues` drops a top-level key only when it is defined in a cross-step branch and no step's schema, resolved by rjsf `retrieveSchema` against the current values, holds it. It repeats until nothing more drops, so a value dropped in one pass stops satisfying later conditions. (not Evaluate each branch's condition separately with ajv; not Drop every field missing from the resolved schemas, same-step ones included) — FR-5 conditions a to d reduce to this, because a selected branch always resolves its field, and using rjsf's own resolver means the rule cannot disagree with what the form renders. Repeating makes chained conditions agree with Review (FR-8).
- Filtered view, not filtered state: `stepsState` keeps every value. Stepper derives `visibleState` once per render and passes it to `Form`'s `formData`, the review step and `onCreate`. `formContext.formData` stays `stepsState`. The function returns its input object when nothing drops. (not Delete dropped keys from `stepsState`; not Keep `formData={stepsState}` on Form and filter only Review and onCreate) — Q1 default: a value returns with its field because state is untouched. Form needs the view too: otherwise a stale value from a hidden step-2 field keeps a step-3 condition selected, showing a field whose value Review then drops.
- Q3: how form data reaches onChange and the query string (checked in code): The default holds, with no extra code. `Stepper` writes nothing to the URL: `useFormDataFromQuery` only reads `window.location.search` once at mount. `FormProps` has no `onChange`, so `handleChange` is the only typed receiver, and it merges `e.formData` over `stepsState`, so the state is the same as today. (not Filter the query-string seed at mount) — Two consequences to know. `e.formData` no longer carries a dropped key, but the merge keeps it in `stepsState`. The only `?formData=` writers are the OngoingTask start-over paths, built from `task.spec.parameters`, so that draft loses dropped values because they were never submitted (FR-5); OngoingTask is not edited.
- Scope of the condition walk (Q2): The walk reads only a step's top-level `if`, top-level `allOf` entries and top-level `dependencies`, and recurses through branches. It never descends into `properties.<name>`. Top-level `oneOf` and `anyOf` are not conditional branches. (not Walk nested object schemas) — Accepted default of Q2: rjsf evaluates a nested object's conditions against that object's own data. The docs say so.
- Review lookup for cross-step `if`: `findSchemaForKey` also adds the keys read by the step's cross-step conditions to its lookup data, never the looked-up key itself. Same-step conditions get no new data. (not Leave the lookup as it is; not Add all of formState to the lookup data) — It passes only `dependencies` keys today, so a field in a cross-step `if` that uses `required`, or in an `else`, is not found: Review falls back to the raw key and skips masking and `ui:backstage.review`. The docs tell authors to use `required` in `if`, so this must work. Passing the looked-up key makes json-schema-library invent a schema for it, which the comment in that function warns about.
- Public API: No export is added or changed: the new functions stay out of `lib/index.ts`, and `ReviewStepProps`, `ReviewStateProps` and `StepperProps` keep their shapes, so API reports do not change. (not Export the helpers from `lib/index.ts`) — NFR-2. `next/index.ts` re-exports `lib`, so any barrel export becomes alpha public API.
- Template editor preview (FR-9): No edit in `plugins/scaffolder`. `TemplateEditorForm` renders the same `Stepper` and passes its `onCreate` values to the dry run, so FR-9 is delivered by the `Stepper` unit. (not Add a TemplateEditorForm test) — `TemplateEditorForm` has no test file today, and a new one would repeat the Stepper cases. The requirement allows no change.
- Property-array dependencies: `dependencies: { a: ['b'] }` and boolean dependency values stay in `dependencies`, unrewritten and outside the drop rule. (not Rewrite them to `if`/`then`) — The requirements define a conditional branch as a schema dependency, and an array entry defines no field. Its target is already on screen, so it is not a dead end.
- `oneOf` dependency options: Each option with a schema for the dependency key becomes `if: { properties: { key: <that schema> }, required: [key] }` with `then` holding the option minus `properties[key]`. Options with no schema for the key are skipped, as rjsf skips them. (not Keep `oneOf` inside the `then` of a single `if`) — `then: { oneOf }` renders rjsf's option selector, not the matching option's fields, and stripping `properties[key]` keeps the earlier-step field out of the later step (FR-4). A value matching no option now blocks nothing, in line with FR-3.
- Release coverage: One new changeset with `'@backstage/plugin-scaffolder-react': minor`. No changeset for `@backstage/plugin-scaffolder`. (not `patch` for scaffolder-react; not Add `@backstage/plugin-scaffolder` to the changeset) — A non-breaking feature in a package at 1.0.0 or higher takes `minor`. `pre.json` holds it in prerelease mode. `plugins/scaffolder` source does not change, and no existing changeset describes this behaviour.

### U01 — create `plugins/scaffolder-react/src/next/lib/crossStepConditions.ts` (codegen)

Behaviour: Classifies each step's conditional branches, rewrites cross-step `dependencies` into `allOf` `if`/`then`, and computes the form values without those hidden by a cross-step condition.

Rules:
1. 1. Local `isObject(value: unknown): value is JsonObject` as in `lib/schema.ts`. Imports: `JsonObject`, `JsonValue` from `@backstage/types`; `ADDITIONAL_PROPERTY_FLAG`, `retrieveSchema`, type `RJSFSchema`, type `ValidatorType` from `@rjsf/utils`; `omit` from `lodash`.
2. 2. Internal `conditionKeys(node)`: the top-level keys a condition schema reads, meaning keys of `properties`, string entries of `required`, keys of `dependencies`, plus the same recursively through object entries of array `allOf`, `anyOf`, `oneOf` and object `not`, `if`, `then`, `else`.
3. 3. Internal `collectBranches(stepSchema)` returns `{ reads: string[]; fields: string[] }[]` by walking `walk(node, reads, inBranch)` from `walk(stepSchema, [], false)`. When `inBranch`, record `{ reads, fields: keys of node.properties }`.
4. 4. In `walk`: for an object `node.if`, compute `branchReads = reads + conditionKeys(node.if)` and walk object `node.then` and `node.else` with `branchReads` and `true`. For each object entry of array `node.allOf`, walk it with `reads` and the same `inBranch`.
5. 5. In `walk`: for each `[key, value]` of `node.dependencies` where `value` is a non-array object, compute `branchReads = reads + key`, walk `value` with `branchReads` and `true`, then for each object entry of array `value.oneOf` walk a copy whose `properties` omit `key`, with `branchReads` and `true`. `walk` never enters `properties.<name>`, `items`, or a `oneOf`/`anyOf` outside a dependency value.
6. 6. Internal `fieldKeys(stepSchema)`: keys of `properties`, keys of `properties` of each object entry of top-level `allOf`, and every branch's `fields`.
7. 7. Internal `earlierFieldKeys(stepSchemas, stepIndex)`: a Set of the `fieldKeys` of every step before `stepIndex`, minus the `fieldKeys` of `stepIndex`. A branch is cross-step when any of its `reads` is in that Set.
8. 8. `rewriteCrossStepDependencies`: take `stepSchemas[stepIndex]`. Rewrite only `dependencies` entries whose key is in `earlierFieldKeys` and whose value is a non-array object. If there are none, return the same schema object.
9. 9. For a rewritten entry, split the value into `oneOf` and the rest. If the rest has any key, add `{ if: { required: [key] }, then: rest }`. For each object option of array `oneOf` whose `properties[key]` is an object, add `{ if: { properties: { [key]: option.properties[key] }, required: [key] }, then: option with key removed from its properties }`.
10. 10. Return a shallow copy of the schema with the added entries after any existing array `allOf`, and with the rewritten keys removed from `dependencies`. Delete `dependencies` when no key remains. Never mutate the input.
11. 11. `getCrossStepConditionKeys`: the unique `reads` of the cross-step branches of `stepSchemas[stepIndex]`. An empty array when there are none.
12. 12. `omitHiddenCrossStepValues`: loop on `values`, starting from `formData`. Candidates are the unique `fields` of the cross-step branches of every step, kept only when the key is an own key of `values`. With no candidates, return `values`, so the input object itself comes back when nothing drops.
13. 13. In each pass, for every step compute `rewritten = rewriteCrossStepDependencies(stepSchemas, index)` and `retrieveSchema(validator, rewritten as RJSFSchema, rewritten as RJSFSchema, values)`. Its resolved keys are the keys of `properties` whose value does not carry `ADDITIONAL_PROPERTY_FLAG`, plus keys of `properties` of each object option in the result's array `oneOf` and `anyOf`.
14. 14. Hidden keys are the candidates in no step's resolved keys. With none, return `values`. Otherwise set `values = omit(values, hidden)` and loop again. The loop ends because each pass removes at least one key.
15. 15. If `retrieveSchema` throws for any step, return `formData` as received, so a broken later step fails when the user reaches it, as it does today.

Exports:
- `function rewriteCrossStepDependencies(stepSchemas: JsonObject[], stepIndex: number): JsonObject`
- `function getCrossStepConditionKeys(stepSchemas: JsonObject[], stepIndex: number): string[]`
- `function omitHiddenCrossStepValues(stepSchemas: JsonObject[], formData: Record<string, JsonValue>, validator: ValidatorType): Record<string, JsonValue>`

Import line: `import { getCrossStepConditionKeys, omitHiddenCrossStepValues, rewriteCrossStepDependencies } from '../../lib/crossStepConditions';`

Style from: `plugins/scaffolder-react/src/next/lib/schema.ts:1-50` — Licence header layout, the `isObject` helper and the way this folder walks a step schema.

### U07 — edit `docs/features/software-templates/input-examples.md` (docs)

Behaviour: Explains for template authors how conditional fields read answers from earlier steps, with examples, hidden-value behaviour and limits.

Rules:
