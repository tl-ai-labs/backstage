## Conventions

- Every new .ts, .tsx and .css file starts with the Apache 2.0 block comment reading 'Copyright 2026 The Backstage Authors', copied from an existing file of the package with the year changed; existing files keep their year.
- Formatting is Prettier with @backstage/cli/config/prettier: 2 spaces, single quotes, trailing commas, 80 columns, no parentheses around a single arrow function parameter.
- plugins/notifications uses @backstage/ui, CSS modules and @remixicon/react. New code there imports nothing from @material-ui. plugins/home-react uses Material UI v4 and keeps doing so.
- CSS modules sit beside their component, are named after it, wrap their rules in '@layer components { }' and use --bui-* tokens.
- In plugins/notifications, import useTranslationRef from '@backstage/core-plugin-api/alpha' and useApi and useRouteRef from '@backstage/core-plugin-api'; toastApiRef comes from '@backstage/frontend-plugin-api'.
- Every user-visible string on the card goes through t() from notificationsTranslationRef. Notification text renders as React text: no dangerouslySetInnerHTML.
- Public additions carry TSDoc. Exports that stay inside the package are tagged @internal.
- Tests are jest under jsdom, with describe and it. Use renderInTestApp and TestApiProvider from @backstage/test-utils, screen and .findBy* queries over waitFor, and no new test ids in the implementation. Write fewer thorough tests with several assertions each.
- Report files are generated by a tooling unit and never typed by hand. yarn.lock is written by yarn install only.
- Never run yarn build, yarn changesets version or yarn release, and never change ESLint, Prettier or TypeScript configuration.

## Decisions

- Compatibility reading of NFR-6: Additive changes are allowed: one optional NotificationsTableProps field and new translation keys. No field, key or export is removed or retyped. (not Pass the highlight through an internal React context so the public prop type does not change) — FR-8 already forces new keys onto the exported translation ref, and FR-17 expects the reports to change, so a context would add code without keeping the surface frozen.
- Refresh logic placement: A new internal hook useNotificationsRefresh holds the signal subscription, the 2000 ms throttle, the single-flight rule and the polling timer. Only the card uses it; the page keeps its existing refresh code. (not Move NotificationsPage onto the hook) — The hook polls when signals are absent, which would change the page, and FR-11 says a page without an id behaves exactly as today.
- Card frame and heading: The card draws its own @backstage/ui Card with the heading t('unreadCard.title'). The widget passes a pass-through Renderer through componentProps so CardExtension adds no InfoCard around it. (not Use the default CardExtension InfoCard with the blueprint title) — The default path shows the blueprint's plain title string, which cannot be translated, and would add Material UI chrome around the card.
- Widget title and description strings (FR-8 boundary): HomePageWidgetBlueprint title and description stay plain English literals: 'Unread notifications' and 'Shows your latest unread notifications'. All strings rendered inside the card are translated. (not Resolve the strings through the translation API inside a makeWithOverrides factory) — The blueprint accepts plain strings at extension definition time, every existing widget does the same, and translated resources are not guaranteed loaded when the factory runs.
- Mark-as-read control: A dedicated ButtonIcon labelled t('unreadCard.markAsRead') on each row. BulkActions is not reused. (not Reuse BulkActions as upstream does) — BulkActions also shows a save action, which is out of scope for the card, and it has no failure handling, which FR-3 requires.
- Mark-as-read failure display: toastApi.post({ title: t('sidebar.errors.markAsReadFailed'), status: 'danger' }), reusing the existing key. The row stays. (not An inline error in the row; not A new translation key with the same text) — This is the failure pattern of NotificationsTable and NotificationsSideBarItem, and the message already exists.
- Severity display: SeverityIcon is used directly, inside a span with role img and aria-label t(`filters.severity.${severity}`); a missing severity means normal. (not Reuse NotificationIcon) — NotificationIcon needs useApp and shows a custom icon in place of the severity, while FR-1 requires the severity to be shown.
- Background refresh failure: The card keeps the last good rows in its own state. useAsyncRetry drops value on failure, so rendering uses that state, and the error state shows only when no rows have ever loaded. (not Render directly from value and error) — FR-2 says a failed background refresh does not replace a list that is already showing.
- Deep link path: `${useRouteRef(rootRouteRef)()}?id=${encodeURIComponent(notification.id)}`, built on the card with no separate helper module. (not A hard-coded /notifications path as upstream has) — FR-4 requires a non-default mount path to work, and one call site does not justify a util file.
- Deep link handling on the page: The page never changes its filters or page number for an id. An item outside the current rows goes first and the rows are capped with slice(0, pageSize); pageSize and totalCount stay as they are. (not Pass pageSize + 1 to the table as upstream does; not Switch the read filter and go to page 0 as upstream does) — FR-10 says the table stays within its page size and the item shows alongside the current rows.
- Highlight marker: The highlighted row's Flex gets aria-current='true' and className styles.highlightedNotification. No scrolling and no focus change. (not A wrapper div with scrollIntoView and focus as upstream does) — FR-9 asks only for a highlight, a single prop change avoids re-indenting the whole cell, and aria-current gives tests a semantic selector with no test id.
- Suspense fallback on the custom Renderer path: Material UI CircularProgress in plugins/home-react. The default path keeps the app's Progress. (not core-components Progress, whose name collides with the local Progress of the default path) — The app's Progress needs useApp, which FR-13 removes from this path, and Gate 1 left default-path cards as they are.
- Card configuration: The card takes optional props limit (default 5) and pollIntervalMs (default 60000). The widget has no settings schema and no other card option. (not A widget settings schema for the count and text limits as upstream has) — The requirements fix the defaults and exclude new list features.
- Legacy export: components/index.ts does not export the card; it loads only through the alpha widget's dynamic import. The widget is defined in alpha.tsx and is not a named export. (not Export the card from the package's main entry point) — A legacy export is out of scope, and components/index.ts feeds the public entry point.
- README: plugins/notifications/README.md does not change. — It already points to the Backstage notifications documentation, and FR-15 changes it only if a pointer is needed.
- Test double for signals: Tests run the real useSignal against a fake signalApiRef registered in TestApiProvider. Leaving the API out is how a test makes signals unavailable. (not jest.mock of @backstage/plugin-signals-react) — This proves the subscription is released on unmount and that availability follows the real hook.
- API report tooling units: U23 compiles and regenerates both packages. U24 reruns extraction without compiling so report-alpha.api.md is also recorded as a step's output. — A tooling unit records one path and the notifications package writes two report files. The home-react reports do not list CardExtension and are expected to stay unchanged.

### U08 — create `plugins/notifications/src/hooks/useNotificationsRefresh.ts` (codegen)

Behaviour: Internal hook that drives a data hook's retry from notification signals, with a polling fallback, one throttle and no overlapping refresh.

Rules:
1. Module constants: ThrottleDelayMs = 2000 and DefaultPollIntervalMs = 60_000.
2. Import useSignal from '@backstage/plugin-signals-react'. It returns { lastSignal: JsonObject | null; isSignalsAvailable: boolean }. Call useSignal('notifications') without a generic, as NotificationsPage does.
3. Hold a pending boolean in useState and create one throttled setter with useMemo(() => throttle(setPending, ThrottleDelayMs), []); throttle is the default lodash/throttle, so leading and trailing edges both fire.
4. An effect with cleanup calls the throttled setter's cancel() on unmount.
5. An effect runs retry() and then setPending(false) only when pending is true and loading is false, so no refresh starts while one is running.
6. An effect calls the throttled setter with true when lastSignal && lastSignal.action.
7. An effect returns undefined when isSignalsAvailable is true; otherwise it starts setInterval calling the throttled setter with true every pollIntervalMs, and its cleanup clears the interval.
8. requestRefresh is a useCallback over the same throttled setter, so a manual request shares the throttle window with signals.

Exports:
- `function useNotificationsRefresh(options: { loading: boolean; retry: () => void; pollIntervalMs?: number }): { requestRefresh: () => void }`

Import line: `import { useNotificationsRefresh } from '../../hooks';`

Style from: `plugins/notifications/src/components/NotificationsPage/NotificationsPage.tsx:143-159` — The throttled refresh pattern the hook carries over, plus cancel and polling.
