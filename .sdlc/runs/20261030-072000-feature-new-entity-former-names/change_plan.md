## Decisions

- Annotation key for the former-refs declaration: backstage.io/former-entity-refs — a well-known backstage.io-prefixed key, valid by construction under isValidAnnotationKey, exported as ANNOTATION_FORMER_ENTITY_REFS from packages/catalog-model/src/entity/constants.ts. (not backstage.io/former-names (names alone cannot express a namespace or kind move, which AC-18 requires); not backstage.io/previous-refs (no repo precedent for 'previous'; 'former' is the brief's word); not a new metadata field outside annotations (CON-2: annotation keys are unconstrained and already flattened into the search table; a new metadata field needs schema and index work NFR-3 forbids)) — The declared value is a list of entity REFS, not bare names (AC-18 needs namespace moves), and the backstage.io/ prefix is the established well-known namespace (CON-2, FR-1).
- Delimiter and escaping rule for the annotation value: Comma. Entries are split on ',', each entry is trimmed, empty entries after trimming are dropped. There is NO escape mechanism: a comma can never appear inside an entity ref because parseEntityRef's grammar is [<kind>:][<namespace>/]<name> over DNS-label characters, so no entry can legitimately contain one. (not Semicolon or whitespace delimiter (no repo precedent; comma is the precedent per CON-2 and parseEntityFilterString already splits annotation-shaped strings on comma); not A backslash or quoting escape scheme (unreachable code: no valid ref contains a comma, so an escape rule would only ever add a parsing branch no input can exercise); not JSON array inside the annotation string (CON-2 allows it but it is hostile to hand-authored YAML and has no repo precedent)) — CON-2 names comma as the repo's precedent for delimited annotation values, and D-3 requires whitespace tolerance. Ref grammar makes escaping unnecessary rather than merely unspecified.
- Fail-closed semantics for a malformed annotation value: PER-ENTRY fail-closed, never whole-value. parseFormerEntityRefs catches the throw from parseEntityRef per entry and drops only that entry; valid sibling entries still resolve. The function never throws and returns [] for undefined, empty, all-malformed or over-limit input. (not Whole-value rejection on any bad entry (a single typo would silently kill every working redirect on that entity, which is worse for the adopter and harder to diagnose); not Throwing an InputError for the caller to handle (AC-20 requires it to throw nothing on both the backend lookup path and the frontend render path)) — FR-3 and AC-20 require 'yields no resolution candidate and never throws'. Per-entry containment maximises the surviving redirects while still never throwing.
- Bound on the number of former refs one entity may claim: 20, as the exported constant FORMER_ENTITY_REFS_MAX_COUNT. parseFormerEntityRefs returns [] (the whole declaration, not a prefix) when the de-duplicated parsed list exceeds 20. (not No bound (NFR-5 forbids it: the annotation would be an index-flood vector); not Silently truncating to the first 20 (an adopter who declares 25 refs would get 20 working and 5 silently dead links with no signal; refusing the whole declaration is a visible, diagnosable failure)) — NFR-5 requires a bound. 20 is far above any real rename history and far below a flood. Whole-declaration refusal rather than truncation keeps the failure legible.
- Whether a new catalog-backend HTTP route is needed: NO new route. Former-ref resolution is composed entirely from the EXISTING POST /entities/by-query endpoint, reached through CatalogApi.queryEntities with a `query` FilterPredicate. No change to openapi.yaml, no regeneration of src/schema/openapi/generated/**, no `generate` tooling step. (not A new GET /entities/resolve-ref route (CON-3: hand-edited OpenAPI spec plus a generate step for both the router and the client, and the generated dir is off-limits in the write contract anyway); not A new CatalogApi member (D-1, CON-1, AC-21 forbid it outright)) — CON-3 makes a route expensive and CON-5 makes it unnecessary: annotations are already flattened into the `search` table and already queryable through the FilterPredicate path. D-1 forbids a new interface member, so the lookup ships as a plain exported function over queryEntities.
- Where former-ref resolution is implemented so no CatalogApi member is added: A plain exported async function resolveFormerEntityRef(catalogApi, formerRef) in packages/catalog-client/src/resolveFormerEntityRef.ts, taking a CatalogApi as its FIRST ARGUMENT and calling only existing members (queryEntities). Exported from the package index as a free function. (not A required or optional CatalogApi interface member (D-1, CON-1, FR-11, AC-21: CatalogService/CatalogServiceMock in plugins/catalog-node and the `as CatalogApi` cast in plugins/catalog-import are outside the write contract and would fail yarn tsc); not A subclass or wrapper of CatalogClient (re-types the surface and still breaks the mocks)) — FR-10/FR-11 require the lookup without touching the interface. A free function over an injected CatalogApi leaves CatalogApi, CatalogClient, CatalogService, CatalogServiceMock and InMemoryCatalogClient byte-identical.
- The predicate shape the resolution query uses: THE SHAPE TO USE, the only one any unit may emit: a single queryEntities call with query = { $all: [ { [key]: true }, { $not: { kind: 'user' } } ] } and limit: 2, where `key` is the synthetic per-entry search key `metadata.annotations.backstage.io/former-entity-refs.<normalized-full-ref>`, always composed from the exported key-prefix constant and never hand-formatted. Those per-entry rows are written inside buildEntitySearch (see that unit). REJECTED ALTERNATIVE — DO NOT COPY: { 'metadata.annotations.backstage.io/former-entity-refs': { $contains: <formerRef> } }; a primitive $contains target compiles to an exact `value` match (applyPredicateEntityFilterToQuery.ts:186-190) against the ONE row holding the entire comma-delimited string, so matching one entry inside that string is impossible. (not $contains on the raw annotation value (matches only an entity whose entire annotation value equals the one ref — breaks AC-18's multi-ref case); not $hasPrefix on the raw value (matches only when the wanted ref is the FIRST entry, and would mis-match a ref that is a string prefix of another); not A client-side scan over all entities carrying the annotation (NFR-2 forbids a scan)) — CON-5 gives the index for free but only at exact (key, value). Per-entry synthetic rows are what make an index-backed exact match possible for every entry (NFR-2, AC-18), and they are written inside buildEntitySearch, which performStitching already calls at the one choke point (CON-4) — no new table, no migration, no new query shape (NFR-3, CON-10).
- Exact synthetic search key and value for a per-entry former-ref row: key = `metadata.annotations.backstage.io/former-entity-refs.<normalized-full-ref>` and value = `true`, mirroring buildEntitySearch's existing array-item convention (`metadata.tags.java` -> true). The ref is the lowercased full `kind:namespace/name` produced by stringifyEntityRef. Rows whose key exceeds the existing MAX_KEY_LENGTH of 200 are dropped by mapToRows, which is already the correct fail-closed behaviour. (not A fresh top-level key namespace such as `former-refs.<ref>` (invents a key space outside the metadata.annotations.* tree, which breaks the mental model that every search key is a path into the entity); not key = the annotation path with value = the ref (collides with the row buildEntitySearch already emits for the raw annotation string, whose value is the whole delimited list, and the (entity_id, key, value) unique index makes the two indistinguishable in intent)) — Reusing the existing `<path>.<item>` -> true convention means the row is indistinguishable in shape from a tag row, is served by the existing search_key_value_entity_idx, and is matched by the existing $contains-on-primitive compilation with zero changes to applyPredicateEntityFilterToQuery.
- How kind: User is excluded structurally (D-2, FR-22, AC-17): TWO independent structural gates, both required. (1) WRITE side: buildEntitySearch emits no per-entry former-ref row at all when entity.kind lowercases to 'user', so a User's own declaration is never indexed. (2) READ side: resolveFormerEntityRef refuses before issuing any request when the requested former ref parses to kind 'user', and its predicate carries { $not: { kind: 'user' } } so a non-User entity cannot launder a User former ref. (not Read-side check only (a User's rows would sit in the index, so any future caller composing its own predicate re-enables the disclosure — D-2 requires that no later caller can); not Write-side check only (a Component could claim `user:default/old-name` as its former ref and capture the redirect); not A documentation warning (D-2 explicitly rejects this: 'Not a documentation warning')) — FR-22 requires the exclusion be enforced so that 'no adopter misconfiguration, and no later caller, can re-enable it'. One gate cannot deliver that; the write gate keeps the data out and the read gate keeps the query honest.
- Ambiguity and live-entity precedence (FR-5, FR-6, FR-7): resolveFormerEntityRef requests limit: 2 and returns { status: 'unknown' } whenever the result count is not exactly 1 — zero means nothing claims it, two or more means contested. It is called ONLY after a direct lookup has already missed, so a live holder of the ref always wins by never reaching this code (FR-5). A claim on a ref a live entity holds is inert because the direct lookup succeeds first (FR-7). (not Ordering the candidates and picking the first (FR-6 requires ambiguous -> nothing, not arbitrary choice); not Checking the ref's liveness inside resolveFormerEntityRef before querying (an extra round trip on every miss; the caller already knows the direct lookup missed, which is the only reason it calls this at all — NFR-1, FR-16)) — limit: 2 makes 'exactly one' decidable in a single query. Post-miss-only invocation is what keeps the hot path untouched (NFR-1) and makes live-entity precedence structural rather than a comparison.
- Permission equivalence and information leak (FR-8, NFR-4): Resolution issues no privileged call: queryEntities runs through AuthorizedEntitiesCatalog exactly as every other read does, which ANDs the CONDITIONAL permission predicate as { $all: [permissionFilter, requestFilter] }. A caller who may not read the target gets zero rows, which resolveFormerEntityRef reports as { status: 'unknown' } — byte-identical to a ref nothing claims. The notice text names only the former ref the viewer already typed, plus the target they are now permitted to load. (not A dedicated resolution endpoint with its own permission check (CON-3 cost, and a second authorization path is a second place for the two cases to diverge); not Returning a distinguishable 'forbidden' status (NFR-4 forbids a distinct error message or a redirect to a URL the viewer cannot load)) — Q3 and FR-8 require the two cases be indistinguishable BY CONSTRUCTION. Reusing the ordinary read path with a single result shape for both achieves that without a branch that could be got wrong.

It gains a second conditional step that runs ONLY when the direct getEntityByRef resolved to undefined, and on success calls navigate(targetUrl, { replace: true }). Both systems already import this one hook (legacy CatalogEntityPage.tsx, alpha alpha/components/CatalogEntityPage.tsx), so one implementation serves both (CON-6, D-6, FR-14). (not Rebuilding the target from scratch and dropping the sub-path (AC-19 requires .../old-name/docs -> .../new-name/docs); not Appending a ?formerRef= query parameter (pollutes a URL the user may re-share, and would survive a copy-paste as a permanent query arg); not A module-level or context variable (does not survive the remount the navigation causes)) — Prefix substitution is the only construction that preserves an arbitrary tab sub-path, and react-router navigation state is the idiomatic carrier for a one-shot arrival signal that must not pollute the URL (FR-15's no-loop requirement falls out: state is consumed once and absent on reload).

(not A redirect counter or a depth query parameter (observable in the URL and a weaker guarantee than 'the destination resolves directly')) — FR-15 requires the destination never re-trigger resolution for the same ref. Guard (1) makes that true by construction; (2) additionally prevents duplicate in-flight requests across the remounts a replace-navigation causes.

### U02 — create `packages/catalog-model/src/entity/formerEntityRefs.ts` (codegen)

Behaviour: Parses the comma-delimited former-entity-refs annotation value into a normalized, de-duplicated, order-stable list of full entity refs, failing closed per entry and never throwing.

Rules:
1. 1. Export one function, `parseFormerEntityRefs(value: string | undefined)`, returning `string[]`. It MUST NOT throw for any input whatsoever, including undefined, null cast as the parameter type, the empty string, and arbitrary junk.
2. 2. Return `[]` immediately when `value` is not a non-empty string after trimming.
3. 3. Split the value on the ',' character. There is NO escape syntax: a valid entity ref can never contain a comma because parseEntityRef's grammar is [<kind>:][<namespace>/]<name> over DNS-label characters. Do not implement quoting or backslash handling.
4. 4. For each split entry: trim leading and trailing whitespace; skip the entry when the trimmed result is empty.
5. 5.
