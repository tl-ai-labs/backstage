# Requirements — Catalog entity former names and rename redirects

Run: `20261109-123528-feature-new-entity-former-names` · Job: `feature-new` · Brief: `intent_brief.md`
Upstream request: backstage/backstage#5231.

## Problem

A catalog entity's URL is built from its kind, namespace and name. Renaming an entity, or moving it to another
namespace, breaks every link that pointed at it: `/catalog/default/component/old-name` shows "Entity not found",
and TechDocs links (`/docs/default/component/old-name/...`) break the same way. This feature lets an entity
declare the refs it used to have, lets the catalog resolve an old ref to the current entity safely, and makes
the entity page and the TechDocs reader redirect old links to the renamed entity with a notice.

## In scope

1. A well-known annotation in `@backstage/catalog-model` that declares an entity's former refs.
2. Indexing of those former refs in `@backstage/plugin-catalog-backend` (new table + migration), kept in sync
   with the entity as it is stitched and removed when the entity is deleted.
3. A new, separate catalog REST endpoint that resolves a former ref to the current entity, with conflict rules
   and permission checks; added to the catalog OpenAPI spec and the generated server and client code.
4. A new `CatalogApi` / `CatalogClient` method in `@backstage/catalog-client` that calls that endpoint.
5. Redirect + "renamed" notice on the catalog entity page (old and new frontend systems) when the URL's ref is
   not found but resolves as a former ref.
6. Redirect + "renamed" notice in the TechDocs reader when the URL's entity ref is not found but resolves as a
   former ref, keeping the rest of the docs path.
7. Documentation (well-known annotations page, catalog and TechDocs feature docs) and changesets for every
   published package whose behavior or API changes.
8. Backend unit tests and frontend jsdom tests for the above.

## Out of scope

1. Automatic detection of renames without an explicit declaration (non-goal in the brief).
2. Redirecting routes other than the catalog entity page and the TechDocs reader (for example the scaffolder,
   API docs pages or arbitrary plugin routes).
3. Any change to the existing `GET /entities/by-name/:kind/:namespace/:name` endpoint, `getEntityByRef`,
   `getEntitiesByRefs`, or their query paths and performance.
4. Changing an entity's kind as a rename: a former ref with a kind different from the entity's own kind is
   ignored (see FR-2).
5. Following chains (A renamed to B, B renamed to C): each entity lists all of its own former refs; the catalog
   resolves one hop only.
6. Rewriting relations or other entities' references that still point at the old ref.
7. `.gitignore` changes (Gate 0 decision: `.sdlc/` is not added).
8. Editing generated API reports (`report*.api.md`) by hand; they are regenerated by the project's tooling.

## Functional requirements

### Module: catalog-model (`packages/catalog-model`)

- **FR-1** Export a new well-known annotation constant for former refs, value `backstage.io/former-refs`, with
  TSDoc. The annotation value is a comma-separated list of entity refs; whitespace around each item is
  ignored and empty items are skipped.
- **FR-2** Export a helper that, given an entity, returns its former refs as normalized, lowercase-compared
  `CompoundEntityRef`s (or stringified refs): a short ref (`old-name`) or `namespace/name` ref is completed
  with the entity's own kind and namespace; items that do not parse, whose kind differs from the entity's own
  kind, or that equal the entity's own current ref are dropped; duplicates are removed.

### Module: catalog-backend (`plugins/catalog-backend`)

- **FR-3** A new knex migration (dated after `20261007000000_stitch_failure_count.js`) creates a table that
  maps a normalized former entity ref to the entity that claims it (by entity id, with a foreign key that
  cascades on entity deletion), with an index on the former ref column. Migrations must have a working `down`.
- **FR-4** When an entity is stitched (final entity written), its rows in the former-refs table are replaced
  with the refs FR-2 returns for the stitched entity, in the same transaction or at the same point the search
  rows are written. An entity with no annotation has no rows. Removing the annotation removes the rows.
- **FR-5** A new endpoint, separate from by-name, resolves a former ref: for example
  `GET /entities/by-former-name/:kind/:namespace/:name`. It is defined in `src/schema/openapi.yaml` and the
  generated router/client code is regenerated with the package's own OpenAPI generator, not hand-written.
- **FR-6** Conflict rule — live name wins: if an entity currently exists with exactly the requested ref, the
  former-ref lookup returns not found (404). An entity can never take over a name that a live entity holds.
- **FR-7** Conflict rule — ambiguity: if more than one entity claims the requested former ref, the lookup
  returns not found (404) rather than picking one, and the backend logs this at debug or warn level without
  failing processing.
- **FR-8** Permissions: the lookup only returns the target entity when the caller is allowed
  `catalog.entity.read` on that target (through the existing authorized catalog / permission integration,
  including conditional decisions). When the caller is not allowed, the response is the same 404 as for an
  unknown ref, so the existence and new name of the entity is not revealed.
- **FR-9** The lookup response returns the current entity in the same shape as by-name, so the caller can read
  its current kind, namespace and name. The request is audited with the catalog auditor like the other
  entity-fetch routes (a distinct `queryType`).

### Module: catalog-client (`packages/catalog-client`)

- **FR-10** Add a method to the `CatalogApi` interface and `CatalogClient` (for example
  `getEntityByFormerRef(entityRef, options?)`) that accepts a string or `CompoundEntityRef`, calls the new
  endpoint, and resolves to the current `Entity`, or `undefined` on 404. Other errors are thrown like
  `getEntityByRef` does. Any in-repo `CatalogApi` implementations or mocks that must implement the interface
  (for example in `plugins/catalog-react` test utilities, if inside the allowlist) are updated so `yarn tsc`
  passes; adding a required method to the published interface is treated as a breaking change only if the
  architect cannot make it optional.

### Module: catalog (`plugins/catalog`) and catalog-react (`plugins/catalog-react`)

- **FR-11** On the catalog entity page, when loading the entity from the URL finds no entity, the page asks
  the catalog for a former-ref match for the URL's ref. On a match it navigates (history replace) to the
  current entity's page, preserving the rest of the path (sub-route/tab) and the query string, and marks the
  navigation as a rename redirect (for example a query parameter or router state carrying the old ref). With
  no match, the existing "Entity not found" behavior is unchanged.
- **FR-12** On the entity page reached through a rename redirect, a dismissible notice is shown:
  "This entity was renamed from `<old ref>`." (wording may follow existing style), using the existing notice
  pattern (for example like `EntityOrphanWarning`). Without the marker, no notice is shown.
- **FR-13** FR-11 and FR-12 apply to both the old frontend system (`CatalogEntityPage` / `useEntityFromUrl`)
  and the new frontend system entity page (`plugins/catalog/src/alpha`). Shared helpers may live in
  `@backstage/plugin-catalog-react` if both plugins need them.

### Module: techdocs (`plugins/techdocs`)

- **FR-14** In the TechDocs reader (`/docs/:namespace/:kind/:name/*`), when the entity for the URL's ref is
  not found, the reader asks the catalog for a former-ref match. On a match it navigates (history replace) to
  the current entity's docs URL, keeping the remaining docs path, hash and query string. With no match, the
  existing not-found behavior is unchanged.
- **FR-15** The docs reached through a rename redirect show a notice "This entity was renamed from
  `<old ref>`", reusing or matching the existing `TechDocsRedirectNotification` style.

### Documentation and release

- **FR-16** Document the annotation in `docs/features/software-catalog/well-known-annotations.md`: format,
  defaulting of kind/namespace, same-kind rule, conflict rules (FR-6, FR-7), permission behavior (FR-8), and
  the frontend redirects. Mention the TechDocs redirect in `docs/features/techdocs/` where reader behavior is
  documented. TSDoc on every new exported symbol.
- **FR-17** Changesets in `.changeset/` for each changed published package, with bump levels per AGENTS.md
  (new API at >= 1.0.0 → `minor`; below 1.0.0 → `patch`; prerelease `-next` packages follow their base
  version), written for adopters without internal symbol names.

## Non-functional requirements

- **NFR-1** Existing by-name lookups and the stitching hot path keep their performance: the new endpoint is a
  separate query using the indexed former-ref column; by-name code paths are not modified. The former-refs
  write during stitching is one delete + one batched insert per entity, and only touches rows of that entity.
  (`plugins/catalog-backend/CLAUDE.md` asks for the catalog DB performance check on any DB change; the senior
  review checks the new query and index against it.)
- **NFR-2** Works on every database the catalog supports (PostgreSQL, SQLite, MySQL): portable knex schema and
  queries only; refs are stored normalized (lowercase) so lookups are case-insensitive like entity refs.
- **NFR-3** `yarn tsc` and `yarn lint:all` pass; Prettier formatting matches the repo.
- **NFR-4** Every new source file has the Apache 2.0 header with year 2026; existing headers unchanged.
- **NFR-5** Code style matches each package's existing conventions (STYLE.md, each package's patterns).
- **NFR-6** The redirect does not loop: a redirect target that itself is not found does not trigger a second
  former-ref lookup chain beyond one hop.
- **NFR-7** API reports (`report*.api.md`, `report.sql.md`) are not edited by hand; noted for regeneration with
  `yarn build:api-reports` / the SQL report tooling before PR (final report).

## PII inventory

| Field | Sensitivity | Protection |
|---|---|---|
| Former entity refs (kind/namespace/name) | Low: catalog metadata, same class as current entity names | Same permission checks as the target entity (FR-8); 404 on deny so a hidden entity's new name is not revealed |

No personal data, secrets or credentials are introduced.

## Role matrix

| Role | Resource | Action |
|---|---|---|
| Catalog ingestion (entity providers / locations) | Former-refs annotation | Declare former refs on the entities it ingests (existing catalog trust model; no new authority) |
| Any caller with `catalog.entity.read` on the target | Former-ref lookup endpoint | Resolve an old ref to the current entity |
| Caller without read on the target | Former-ref lookup endpoint | Receives 404, indistinguishable from unknown ref |
| Frontend user | Entity page / TechDocs reader | Redirected only when the lookup returns an entity they may read |

## Acceptance criteria

- **AC-1** catalog-model unit tests: the helper (FR-2) completes short refs with the entity's kind and
  namespace, trims whitespace, drops unparseable, other-kind and self refs, and de-duplicates.
- **AC-2** catalog-backend tests: stitching an entity with the annotation writes its former-ref rows; changing
  or removing the annotation replaces/removes them; deleting the entity removes them (FR-3, FR-4).
- **AC-3** catalog-backend tests: the lookup returns the current entity for a declared former ref; returns 404
  when a live entity holds the requested ref (FR-6); returns 404 when two entities claim the same former ref
  (FR-7).
- **AC-4** catalog-backend tests: the lookup returns 404 when the permission decision denies read on the
  target, and returns the entity when allowed (FR-8); the router test covers the new route.
- **AC-5** catalog-client test: the new method calls the new endpoint and returns the entity, and returns
  `undefined` on 404 (FR-10).
- **AC-6** catalog jsdom tests: visiting an old ref on the entity page redirects to the current entity and
  shows the renamed notice; an unknown ref with no match still shows "Entity not found" (FR-11, FR-12, FR-13).
- **AC-7** techdocs jsdom tests: visiting an old ref in the TechDocs reader redirects to the current entity's
  docs path (keeping the sub-path) and shows the renamed notice; no match keeps the existing not-found
  behavior (FR-14, FR-15).
- **AC-8** The well-known annotations doc describes the annotation and its rules, and changesets exist for
  every changed published package (FR-16, FR-17).

## Assumptions (stated for Gate 1)

- A1 Annotation name `backstage.io/former-refs` (comma-separated refs) rather than a new `metadata` field, so
  no schema change to `EntityMeta` is needed and older clients ignore it.
- A2 Who may claim a former name: any entity the catalog ingests, under the catalog's existing ingestion trust
  model; hijack is prevented by FR-6 (live name wins) and FR-7 (ambiguous claims resolve to nothing), and
  information leaks by FR-8.
- A3 Same-kind only (Out of scope 4); cross-namespace claims are allowed.
- A4 The OpenAPI generator (`yarn --cwd plugins/catalog-backend generate`) is run as a tooling step to produce
  the generated server and client code, inside the allowlist.

## Gate 1 decisions (Vaibhav, approved)

- A1 to A4 accepted as stated.
- The new `CatalogApi` method is **optional** on the interface (non-breaking; `minor` bump for
  `@backstage/catalog-client`). `CatalogClient` implements it.
