# Intent Brief — bugfix — useRouteRef in app root elements crashes during startup

## Context
In the new frontend system, app root elements (`app/root.elements`), such as a banner, that call
`useRouteRef` while the app is starting crash with `No path for <routeRef>`.

During startup, `prepareSpecializedApp` builds a partial tree. Deferred subtrees are skipped.
`instantiateAndInitializePhaseTree` (`packages/frontend-app-api/src/wiring/phaseApis.tsx`)
initializes `RouteResolutionApiProxy` from the route info of that partial tree. When a route ref's
own path is known but an ancestor's path is not yet registered, `resolveBasePath` in
`packages/frontend-app-api/src/routing/RouteResolver.ts` throws `No path for ${ref}` (line ~153).

There is a second problem. When the app is finalized, the same `RouteResolutionApiProxy` instance
is re-initialized with the full route info. `useRouteRef` (`packages/frontend-plugin-api/src/routing/useRouteRef.tsx`)
memoizes on `[routeResolutionApi, routeRef, pathname]`, and the API identity doesn't change. An
element rendered during startup therefore never picks up the resolved link after finalization,
even once it stops crashing.

Reported by the user: "In the new frontend system, app root elements that call useRouteRef during
startup crash with "No path for routeRef"."

## Goal
1. During startup, `useRouteRef` in an app root element does not crash the app. While a route can't
   be resolved yet, it returns `undefined`, as its TSDoc promises.
2. An app root element, such as a banner, that rendered during startup renders and gets the correct
   link from `useRouteRef` once the app is finalized, with no render loops. This probably needs a way
   for the route resolution API to tell consumers that it has changed, such as an optional lifecycle
   or subscription method that `useRouteRef` listens to. The architect decides the exact shape.

## Acceptance criteria
1. A new integration test renders an app whose app root element (a banner) calls `useRouteRef` on a
   route ref that can't be resolved during startup. Before the fix it fails with `No path for ...`.
   After the fix:
   - The banner renders.
   - After finalization, it shows the correct link.
   - It doesn't keep re-rendering (render count stays bounded).
2. During startup the hook returns `undefined` instead of throwing.
3. The run's test command passes, run verbatim:
   `CI=true yarn test packages/frontend-app-api packages/frontend-plugin-api && yarn tsc && yarn lint:all && yarn build:api-reports`
4. The API reports match the final public API, and any new API is documented in TSDoc and the docs
   above.
5. Patch changesets for `@backstage/frontend-app-api` and `@backstage/frontend-plugin-api` describe
   the fix in language for adopters.
