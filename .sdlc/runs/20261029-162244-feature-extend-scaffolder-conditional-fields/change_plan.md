## Decisions

- Where cross-step resolution lives: One new pure module, plugins/scaffolder-react/src/next/lib/conditionalSchema.ts, exporting `resolveStepSchema(stepSchema, formState)` and `pruneUnreachableFormState(stepSchemas, formState)`. Stepper.tsx calls both; ReviewState/util.ts uses its own narrow helper from the same module. (not Resolving inside useTemplateSchema.ts (it has no access to live form state — it only sees the manifest); not Resolving inline in Stepper.tsx (untestable as a pure function, and FR-2 demands a pure function of (step schema, accumulated state)); not A new React hook (resolution must also run from ReviewState/util.ts, which is not a component)) — FR-2 requires resolution be a pure function of (step schema, accumulated form state); a plain module is directly unit-testable and reusable by both the Stepper and the review step.
- How a cross-step condition is made resolvable: Stub injection into an isolated probe schema. For each governing key referenced by a condition but NOT declared in the step's own `properties`, build a throwaway probe `{type:'object', properties:{[key]:{}}, dependencies:{[key]: <that dependency>}}` (or `{properties:{<stubs>}, if, then, else}`), hand it to RJSF `retrieveSchema` with the accumulated form state, then merge only the NEWLY surfaced properties and required entries back into the step schema and drop the consumed condition. (not Injecting the stub into the step schema itself and rendering that (the injected governing property then renders as a duplicate of the earlier step's question); not Merging every earlier step's properties into the step schema (renders every earlier field again, and breaks `ui:order`, which throws when properties are absent from the order list); not Passing the whole accumulated state as `rootSchema` to RJSF (rootSchema is a schema, not data; it changes nothing)) — Verified against @rjsf/utils 5.24.13: processDependencies skips any dependency whose key is absent from `resolvedSchema.properties` when the step has a `properties` key at all, which is exactly the defect. An isolated probe satisfies that guard without polluting the rendered schema, and the probe's own stub key is stripped from the result so nothing extra renders.
- Which conditional forms resolve cross-step: `dependencies` (object, oneOf-wrapped, and array/required-only forms) and root-level `if`/`then`/`else`. Nested `anyOf`/`oneOf`/`allOf` inside those branches resolve transitively because `retrieveSchema` handles them. (not Adding a bespoke `ui:backstage` visibility option; not Supporting conditions nested under a step's own object-typed property) — NFR-5 restricts the mechanism to standard JSON Schema. Verified: both forms resolve correctly through the probe, including an array dependency that only adds `required`.
- The additive-identity rule for resolution: `resolveStepSchema` returns the SAME object reference it was given whenever the step declares no cross-step condition — no conditions at all, or conditions whose governing keys are all in the step's own `properties`, or a step with `dependencies` and no `properties` key. (not Always returning a fresh resolved object; not Deep-cloning the step schema on every call) — FR-3 demands byte-identical behaviour for existing templates and NFR-6 forbids per-keystroke deep cloning. Reference equality also keeps Stepper's useMemo and useTransformSchemaToProps from re-rendering. Verified: a step with `dependencies` but no `properties` key is already resolved correctly by RJSF today, so it must be left alone.
- Review-step data argument (FR-9): Replace findSchemaForKey's `data` construction with `pickConditionData(schema, formState)` from the new module: collect every key referenced by the step's conditions (`dependencies` keys, plus `if.properties` keys and `if.required` entries, recursing through then/else/allOf/anyOf/oneOf), then copy just those keys from the accumulated formState. (not Passing the whole accumulated formState as `data`; not Keeping the current dependencies-only construction and adding a separate cross-step pass) — Verified: passing the whole formState makes json-schema-library's createSchemaOf synthesise a schema for ANY key via additionalProperties, so findSchemaForKey returns the FIRST step for every key — that breaks four existing util.test.ts cases. Selecting only condition-referenced keys keeps all five existing cases green and fixes the if/then case, which returns undefined today because the current code only ever populates `dependencies` keys.
- Dropping stale values (FR-7): `pruneUnreachableFormState(stepSchemas, formState)` runs on every form change and on back-navigation. A key is dropped only when all three hold: it is declared ONLY inside some step's conditional subschema (never in any step's top-level `properties`), it is absent from every step's resolved properties under the current state, and it is present in formState. Returns the same formState reference when nothing is dropped. (not Enabling RJSF `omitExtraData`/`liveOmit` (they are deliberately destructured out at Stepper.tsx:180-181 and the test that depended on them is skipped as broken); not Replacing rather than merging in handleChange (destroys every other step's answers — breaks 'should remember the state of the form'); not Pruning only the active step's conditional keys (AC-3 changes a step-1 answer and then checks the REVIEW step, so the sweep must cover all steps)) — A key declared at any step's top level is a real answer and must survive (that is what the existing back-navigation tests assert). Only a conditional-only key whose condition no longer holds is unreachable. Verified against the mobile-SDK shape: flipping the flag to false drops sdkName and keeps mobile and repo.
- The useTemplateSchema.ts:73 guard (FR-1): Widen the guard so feature-flag stripping rewrites `properties` only when the step actually declares top-level `properties`; when a step has no `properties` key, leave the schema's shape alone instead of writing an empty `properties: {}` over it. (not Removing the guard entirely; not Hoisting conditional properties up into top-level `properties` in the parsed step) — Hoisting would make every conditional field render unconditionally. The parsed `schema` is what RJSF renders, so conditional subschemas must stay inside their conditions; `resolveStepSchema` surfaces them per-render instead. Verified the existing test 'should deal with dependencies and oneOf options' asserts the second step's schema equals exactly `{dependencies: secondStepDependencies}` with no `properties` key, so an empty-properties write must not reappear for that shape.
- Per-step validation (FR-6): Stepper passes the RESOLVED active-step schema to both `<Form schema=...>` and `createAsyncValidators`, computed once per render in a single useMemo keyed on the active step and the accumulated state. (not Resolving for rendering but leaving createAsyncValidators on the raw mergedSchema; not Resolving twice, separately for the form and the validators) — FR-6 requires validation be built from the same schema that was rendered. One memo keeps them identical and satisfies NFR-6.
- Public API surface: The new module's exports are re-exported from next/lib/index.ts, which flows into the package's `/alpha` entry point. This ADDS public alpha API, so `yarn build:api-reports` must be re-run; **/api-report*.md and report*.api.md are off-limits here, so that regeneration is a manual follow-up called out in this run's handover. plugins/scaffolder-react/src/types.ts does NOT change — no existing exported type's shape moves. - Error shape for a condition referencing an unanswered key (FR-4): No error, no throw, no log. The probe resolves to no added properties and no added required entries, so the condition simply does not hold. Every helper in the new module returns a value for every input and throws nothing. (not Throwing on an unresolvable governing key; not console.warn on a governing key answered in no step) — FR-4 states such a condition must be treated as not holding and must not throw. Verified: the probe with an absent governing key yields zero added properties.

### U01 — create `plugins/scaffolder-react/src/next/lib/conditionalSchema.ts` (codegen)

Behaviour: Pure helpers that resolve a wizard step's JSON Schema against the accumulated answers of all steps, so a condition in step N can reference an answer from an earlier step, and that report which answers have become unreachable.

Rules:
1. Declare a module-local `function isObject(value: unknown): value is JsonObject` exactly as lib/schema.ts does. Do not import one.
2. Declare a module-local `const validator = customizeValidator();` at module scope, from '@rjsf/validator-ajv8'. Build it once per module, never per call.
3. Import `retrieveSchema` from '@rjsf/utils'. It is exported from that package's root.
4. `collectGoverningKeys(stepSchema)`: return the set of property names a step's conditions test. Collect every key of `stepSchema.dependencies` when it is an object. When `stepSchema.if` is an object, collect every key of `if.properties` when that is an object, and every string entry of `if.required` when that is an array. Recurse into `then`, `else`, and each object entry of `allOf`, `anyOf`, `oneOf`, and into each object value of `dependencies`, collecting their `dependencies` keys and `if` keys the same way. Never collect a plain `properties` key as governing.
5. `collectConditionalPropertyNames(stepSchema)`: return the set of property names declared ONLY inside conditional subschemas. Walk `dependencies` values, `if`, `then`, `else`, and each object entry of `allOf`, `anyOf`, `oneOf`, recursively; at every node BELOW the root collect the keys of that node's `properties` when it is an object. Never collect the keys of the root's own `properties`.
6. `pickConditionData(stepSchema, formState)`: return a new plain object holding, for each key of `collectGoverningKeys(stepSchema)`, that key's value from `formState` when `formState` has it as an own property. Omit any key `formState` lacks. Never include a key that is not governing.
7. `resolveStepSchema(stepSchema, formState)` returns the SAME `stepSchema` reference, with no copying, when any of: `stepSchema` is not an object; it has no object `dependencies` and no object `if`; it has no own object `properties` key (RJSF already resolves a dependencies-only step correctly, so leave it alone); or every governing key is already a key of its own `properties`.
8. Otherwise `resolveStepSchema` computes, for each governing dependency key NOT in its own `properties`, an isolated probe `{ type: 'object', properties: { [key]: {} }, dependencies: { [key]: stepSchema.dependencies[key] } }`, calls `retrieveSchema(validator, probe, probe, formState)`, and takes from the outcome every `properties` entry except the probe's own stub key, plus every `required` entry except that stub key.
9. When `stepSchema.if` is an object and at least one of its governing keys is absent from the step's own `properties`, resolve it with one further probe `{ type: 'object', properties: <a stub {} per absent governing key>, if: stepSchema.if, then: stepSchema.then, else: stepSchema.else }`, include `then`/`else` only when each is present, and take from the outcome every property and required entry except the stub keys.
10. The returned schema is a shallow copy of `stepSchema` with: `properties` set to the step's own properties followed by the collected additions (an addition never overwrites an own property of the same name); `required` set to the step's own `required` entries followed by the collected additions, de-duplicated, and the `required` key deleted entirely when that list is empty; each consumed cross-step dependency key removed from `dependencies`, and the `dependencies` key deleted when nothing is left in it; and `if`, `then`, `else` deleted when the `if` probe ran. Never mutate `stepSchema` or anything reachable from it.
11. `pruneUnreachableFormState(stepSchemas, formState)` returns the SAME `formState` reference whenever it would drop nothing, including when no step declares a conditional property.
12. A key is dropped by `pruneUnreachableFormState` only when all of: it is in the union of `collectConditionalPropertyNames` over every step; it is NOT a top-level `properties` key of ANY step (a key any step declares at top level is a real answer and always survives); it is absent from the `properties` of EVERY step's `resolveStepSchema(step, formState)` under the current state; and `formState` has it as an own property. Dropping otherwise is a defect.
13. When at least one key is dropped, return a new shallow copy of `formState` without those keys. Never delete a key from the argument.
14. No helper throws for any input. A governing key answered in no step yields no additions and no drops. A malformed subschema (a string, null, an array where an object is expected) is skipped, not an error.
15. No helper logs, and none deep-clones a whole step schema or the manifest.

Exports:
- `function resolveStepSchema(stepSchema: JsonObject, formState: JsonObject): JsonObject`
- `function pruneUnreachableFormState(stepSchemas: JsonObject[], formState: Record<string, JsonValue>): Record<string, JsonValue>`
- `function pickConditionData(stepSchema: JsonObject, formState: Partial<{ [key: string]: JsonValue }>): Partial<{ [key: string]: JsonValue }>`

Import line: `import { resolveStepSchema, pruneUnreachableFormState, pickConditionData } from '../../lib/conditionalSchema';`

Style from: `plugins/scaffolder-react/src/next/lib/schema.ts` — The house shape for a pure JSON Schema walker in this package: module-local isObject type guard, named export function, recursion over properties/items/anyOf/oneOf/allOf/dependencies/then/else, TSDoc with an @alpha tag on each export.

Uses:
- `plugins/scaffolder-react/src/next/components/Stepper/createAsyncValidators.ts:16-52` — Shows how this package imports JsonObject/JsonValue and constructs schema tooling at module scope; the resolved schema this module returns is what gets handed to createAsyncValidators.

Covers: FR-2, FR-3, FR-4, NFR-3, NFR-4, NFR-5, NFR-6

Checks: fmt, lint
