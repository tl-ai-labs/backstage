# Security Review — pass1

## Summary
Scope is the 13 touched files of this brownfield run (client-side scaffolder form rendering/validation only; no server routes, PII entities, auth or audit code in the touched set). The conditional-field capability itself is implemented without injection, prototype-pollution or secret-handling defects: `collectGoverningKeys` / `collectConditionalPropertyNames` walk the schema with `hasOwnProperty`-guarded reads, `resolveStepSchema` is non-mutating, and no credentials appear in any new fixture or doc example. However the run introduces one high-severity **validation bypass**: `createAsyncValidators` is now fed the `ui:`-stripped `step.schema` instead of `mergedSchema`, so **every custom field-extension validator in the wizard silently stops running** (verified by probe: baseline 1 call, post-change 0 calls). Two further defects are confirmed by probe — a silent **data-loss** prune in steps that mix a cross-step condition with a same-step dependency, and a **feature-flag bypass** where a flagged-off property declared inside a conditional branch now renders. On the framing question: conditional visibility is purely client-side and the backend does not reject out-of-condition values, and the new documentation does not say so.

## Findings

| Severity | Category | Location | Issue | Recommendation |
|---|---|---|---|---|
| High | Input validation bypass | `plugins/scaffolder-react/src/next/components/Stepper/Stepper.tsx` L166-174 | `resolvedSchema` is built from `steps[activeStep]?.schema` and passed to `createAsyncValidators`, replacing the previous `steps[activeStep]?.mergedSchema`. `schema` is the output of `extractSchemaFromStep`, which **deletes every `ui:` key** (`lib/schema.ts` L45-48). `createAsyncValidators` dispatches solely on `'ui:field' in definitionInSchema` (`createAsyncValidators.ts` L121/L152), so it now finds no `ui:field` anywhere and runs no validator. Probe on a plain top-level `ui:field` step: baseline validator invoked once, post-change zero times. This disables client-side field-extension validation across all steps (e.g. `RepoUrlPicker` host allow-listing, entity pickers, secret field validators) — not just conditional fields. The suite is green because no existing test asserts a field-extension `validation` callback actually fires. | Keep two resolutions: feed the validator `resolveStepSchema(steps[activeStep]?.mergedSchema ?? {}, stepsState)` (restoring the `ui:`-bearing schema baseline used) and keep the `schema`-derived `resolvedSchema` only for `renderedSchema`. Add a test asserting a field-extension `validation` callback is invoked on Next. |
| High | Data loss / silent drop of user input | `plugins/scaffolder-react/src/next/lib/conditionalSchema.ts` L426-453 (`pruneUnreachableFormState`) | `canResolve` is computed **per step**, but `collectConditionalPropertyNames(step)` then adds *all* conditional property names of that step as drop candidates. In a step that mixes a cross-step `if`/`then` with a same-step `dependencies`, the cross-step `if` makes `canResolve` true, so the same-step dependency's properties also become candidates — yet `resolveStepSchema` leaves same-step `dependencies` unresolved (it returns them untouched in `result.dependencies`), so they never land in `reachableProperties` and are dropped. Probe: step schema with `properties:{repo,creditCard}`, `dependencies.creditCard -> billingAddress`, `if mobile -> then sdkName`; with state `{mobile:true,repo,creditCard:true,billingAddress:'1 Main St',sdkName}` the prune returns `{"mobile":true,"repo":"r","creditCard":true,"sdkName":"MySDK"}` — `billingAddress` is removed while the field is still visible and filled on screen, and it is never submitted. Pure data loss, no user-facing signal. | Make the candidate set per-condition, not per-step: only treat a property name as a drop candidate if it is declared under a subschema whose governing key is *cross-step* (not present in that step's own `properties`). Properties under same-step `dependencies`/`if` must stay in `reachableProperties` as the comment at L448-449 already intends. Add the mixed-step case as a regression test. |
| Medium | Feature-flag bypass / unintended field exposure | `plugins/scaffolder-react/src/next/hooks/useTemplateSchema.ts` L73-85 + `conditionalSchema.ts` L333-338 | The `ui:backstage.featureFlag` filter walks **only top-level `step.schema.properties`**; it never descends into `dependencies`, `then` or `else`. `resolveStepSchema` then hoists properties out of those branches into top-level `properties` *after* the filter has run, so a flagged-off property inside a conditional branch renders. Probe: step 2 with `if mobile -> then {sdkName, 'ui:backstage':{featureFlag:'never-on-flag'}}`, flag inactive — `SDK Name` textbox renders (`PROBE_FF_RENDERED_SDKNAME=true`). The requested confirmation therefore **does not fully hold**: the fix covers top-level properties, but cross-step conditional branches are a new bypass path (before this run a property inside a cross-step `then` never resolved at all, so it could not render). | Either apply the feature-flag filter to the properties `resolveStepSchema` hoists (filter `collectedAddedProperties` against `step.uiSchema[name]?.['ui:backstage']?.featureFlag`), or strip flagged-off properties from conditional subschemas in `useTemplateSchema` before the Stepper sees them. Add a test for a flagged-off property inside `then` and inside `dependencies`. |
| Medium | Misleading security expectation (docs) | `docs/features/software-templates/writing-templates.md`, new section "Show fields based on an answer from an earlier step" | The section states a dropped answer "will not appear on the review step and will not be passed to `spec.steps`" with no caveat that this is a **client-side convenience only**. The scaffolder backend validates submitted `values` against the whole merged parameters schema (`plugins/scaffolder-backend/src/service/router.ts` L590, `jsonschema.validate`) and does not restrict additional properties or re-evaluate which branch was reachable, so a direct `POST /v2/tasks` can supply any value regardless of conditions. A template author can plausibly read this section as "hidden field ⇒ value cannot reach my steps" and use conditional visibility to gate a privileged input. Answering the review question plainly: **yes, the current wording invites that misreading.** | Add one explicit sentence, e.g. "Conditional visibility is a form-rendering convenience, not an access control. The scaffolder API accepts any value permitted by the template's parameter schema, so never rely on a hidden field to protect a value — enforce it in the action or with permissions instead." |
| Low | Silently inert condition | `plugins/scaffolder-react/src/next/lib/conditionalSchema.ts` L176-188 | `resolveStepSchema` only inspects **root-level** `stepSchema.if` / `stepSchema.dependencies`, while `collectGoverningKeys` walks `allOf`/`anyOf`/`oneOf`. A cross-step `if`/`then` wrapped in `allOf` is returned unchanged (`PROBE_ALLOF` shows `properties` still just `{repo}` with `mobile:true`), so the field never appears and the author gets no error. No data loss (such a step takes the `canResolve:false` path and its properties are preserved). The docs only document root-level forms, so this is a gap rather than a defect. | Either resolve root-level `allOf` entries containing `if`/`dependencies`, or state in the docs that cross-step conditions must be declared at the root of a step schema. |
| Info | Prune not applied on step-label jump | `plugins/scaffolder-react/src/next/components/Stepper/Stepper.tsx` L297-305 (`onClick`/`setActiveStep`) and L275-282 (`handleCreate`) | `handleBack`, `handleChange` and `handleNext` prune, but the stepper-label `onClick` jump and `handleCreate` do not. In practice state has already converged through `handleChange`, so no stale value was reproducible; noting it so the invariant "prune runs on every transition" is not assumed where it does not hold. | Optional: prune once inside `handleCreate` before `onCreate(stepsState)` so the submitted payload is pruned by construction rather than by convergence. |

## Passing checks
- No hardcoded credentials/API keys/tokens in any touched file — `grep -rniE "(api[_-]?key|secret|password|token|credential)[ \t]*[:=][ \t]*['\"]..."` across the five touched test files and the doc returns only the Apache licence URL.
- New test fixtures (`conditionalSchema.test.ts`, `Stepper.test.tsx`, `useTemplateSchema.test.tsx`, `ReviewState/util.test.ts`, `TemplateEditorForm.test.tsx`) use synthetic values only (`my-org/my-repo`, `MySDK`, `1 Main St`) — no real credentials.
- Doc examples contain no secrets, tokens or internal hostnames.
- `resolveStepSchema` does not mutate its input (spread-copies `properties`/`required`/`dependencies`); `pruneUnreachableFormState` returns the identical object when nothing is unreachable.
- All schema traversal uses `Object.prototype.hasOwnProperty.call` and `isObject` guards (arrays/null excluded) — no prototype-pollution sink, no dynamic `eval`/`Function`, no `__proto__` write path.
- `retrieveSchema` calls are wrapped in `try {} catch {}`, so a malformed template schema degrades to "condition not met" rather than throwing into the render tree.
- Review-step masking is preserved: `ReviewState.tsx` still resolves `ui:backstage.review.mask`, `show:false` and `ui:widget: password`/`ui:field: secret` → `******` against `mergedSchema`, which retains `ui:` keys; `pickConditionData` only narrows the *data* passed to `getSchema`, not the schema.
- `pickConditionData` copies only condition-governing keys out of form state — strictly narrower than passing full `formState`, no widening of what the review lookup sees.
- Changeset (`.changeset/scaffolder-cross-step-conditional-fields.md`) correctly discloses the value-dropping behaviour to adopters as a `minor`.
- PII fields (`government_id`, `bank_account`, `salary_base`), role-based response masking, audit-log append-only/actor-capture, authn/authz guards, `reports_to` checks, JWT secret sourcing, password hashing cost factor, Helmet, auth rate limiting, global error filter: n/a — not in the touched set (no controller, service, entity, guard, middleware or config file was touched).
- `.env` / `.env.example`: n/a — no env or config file in the touched set.
- Dependency check: n/a — no manifest or lockfile in the touched set, dependencies unchanged this run. `npm audit --omit=dev` not re-run per budget.

## Required fixes before sign-off
1. **Restore field-extension validation** — feed `createAsyncValidators` a `mergedSchema`-derived resolved schema; keep the `schema`-derived one for rendering only. Cover with a test that asserts an extension `validation` callback fires.
2. **Stop the mixed-step prune from dropping same-step conditional answers** — scope drop candidates to cross-step-governed subschemas; add the `dependencies` + cross-step `if` regression case.
3. **Close the feature-flag bypass for hoisted conditional properties** — filter `ui:backstage.featureFlag` on properties lifted out of `dependencies`/`then`/`else`.
4. **Add the non-security caveat to the docs** — one sentence stating conditional visibility is not an access control and the API accepts any schema-valid value.

Items 5 (root-level-only `allOf` gap) and 6 (prune on label jump / before `onCreate`) are advisory and do not need to gate the run.

## Noted (pre-existing, out of scope)
- The `ui:backstage.featureFlag` filter in `useTemplateSchema.ts` not descending into conditional subschemas predates this run; the *cross-step* exposure path it enables is new (finding 3), but the same gap already applied to same-step `dependencies`, which RJSF resolved locally before this change.
- `plugins/scaffolder-backend/src/service/router.ts` validates `values` without restricting additional properties. Pre-existing, untouched; relevant only as the reason finding 4's doc caveat is needed.
