## Decisions

- Cross-step conditional schema resolution helper placement and signature: Add internal helpers resolveStepSchema and getSchemaPropertyKeys in plugins/scaffolder-react/src/next/lib/schema.ts (not re-exported from plugins/scaffolder-react/src/next/lib/index.ts). (not Exporting new helpers from plugins/scaffolder-react/src/next/lib/index.ts or package root; not Duplicating conditional evaluation logic separately in Stepper, createAsyncValidators, and ReviewState) — Keeping the helpers internal to src/next/lib/schema.ts shares one standard JSON Schema resolution implementation across Stepper, createAsyncValidators, useTemplateSchema, and ReviewState without changing public or alpha API reports.
- Standard JSON Schema evaluation and undefined formState values: Strip keys whose value in formState/stepsState is undefined before evaluating JSON Schema conditions (if/then/else, dependencies, allOf, oneOf, anyOf) using @rjsf/validator-ajv8 isValid, while keeping stepsState itself untouched for onCreate. (not Treating missing boolean flags as false when evaluating if: { properties: { flag: { const: true } } } without required: ['flag']; not Mutating stepsState to delete undefined or inactive properties before calling onCreate) — Standard JSON Schema (and backend jsonschema validation) requires required: ['flag'] in if conditions or dependencies keyed on flag so an absent property does not vacuously match, and Out of Scope 5 requires keeping the data passed to onCreate unchanged.
- Preventing earlier-step controlling fields from re-rendering in later steps: When resolving cross-step conditional branches into a step schema, exclude property definitions for keys defined in earlier steps (previousStepKeys), cross-step dependency controlling keys, if-condition keys not in the current step's own properties, and pure discriminator constraint schemas (having const/enum without type or UI metadata) while keeping same-step conditionals intact for RJSF. (not Injecting earlier step property definitions into the current step's schema.properties so RJSF processDependencies can run on them; not Flattening same-step conditionals statically before passing schema to RJSF Form) — Injecting earlier step properties into a later step's schema.properties causes RJSF ObjectField to render the earlier step's input again on the later step, whereas resolving cross-step branches and stripping earlier-step discriminator keys renders only the current step's active fields while preserving live same-step reactivity.
- Filtering inactive conditional fields in ReviewState while preserving unschematized keys: Resolve each step's mergedSchema against the full formState in findSchemaForKey and processSchema, and when findSchemaForKey returns null for a key in formState, omit the key in ReviewState if isKeyDefinedInSchemas reports it is defined in any step schema, otherwise render the formatted key/value fallback. (not Rendering all keys present in formState regardless of whether their schema condition is met; not Dropping all keys where findSchemaForKey returns null even when schemas is empty or the key is not defined in any schema) — Conditional fields from inactive branches (including stale answers left in stepsState after navigating back and changing an earlier answer) are defined in step schemas and must be hidden when inactive, whereas existing callers/tests pass unschematized keys or empty schemas arrays and expect the fallback row.

### U01 — edit `plugins/scaffolder-react/src/next/lib/schema.ts` (codegen)

Behaviour: Provide getSchemaPropertyKeys and resolveStepSchema helpers to collect step property keys and resolve cross-step (and optionally all) JSON Schema conditional constructs against formData without re-rendering earlier-step controlling fields.

Rules:
1. 1. Import JsonObject and JsonValue from '@backstage/types', stringify and parse from 'flatted', FieldValidation and UiSchema from '@rjsf/utils', and customizeValidator from '@rjsf/validator-ajv8', and instantiate a module-level validator via customizeValidator().
2. 2. Export type ResolveStepSchemaOptions = { previousStepKeys?: Set<string>; resolveAll?: boolean }.
3. 3. Export getSchemaPropertyKeys(schema: JsonObject): Set<string> which collects top-level property keys defined in schema.properties and recursively in conditional branches (then, else, allOf, oneOf, anyOf, and object values of dependencies), skipping schema.if and skipping any branch property whose definition is a pure discriminator constraint (an object having 'const' or 'enum' and lacking 'type', 'title', 'properties', 'items', 'ui:field', and 'ui:widget').
4. 4. Export resolveStepSchema(inputSchema: JsonObject, formData: Partial<Record<string, JsonValue>> = {}, options?: ResolveStepSchemaOptions): JsonObject which deep-clones inputSchema via parse(stringify(inputSchema)), builds cleanData by recursively omitting keys whose value is undefined from formData, and resolves conditional constructs on the step object schema.
5. 5. In resolveStepSchema, determine ownKeys as the keys of schema.properties that are not in options?.previousStepKeys; treat a conditional construct as cross-step (to be resolved when options?.resolveAll is false) when it references any key in options?.previousStepKeys or any key not in ownKeys (for dependencies[depKey]: depKey; for if: keys in if.properties or if.required; for oneOf/anyOf/allOf: any branch referencing a key in previousStepKeys or a discriminator/if/dependency key not in ownKeys). When options?.resolveAll is true, resolve all conditional constructs.
6. 6. For if/then/else to be resolved: evaluate validator.isValid(schema.if as JsonObject, cleanData, schema) using standard JSON Schema semantics (so an if without required matches when the property is absent in cleanData, while an if with required does not); remove if, then, and else from schema, and merge the chosen branch (then when valid, else when invalid) into schema while excluding previousStepKeys and any keys referenced in if.properties or if.required that are not in ownKeys.
7. 7. For dependencies[depKey] to be resolved: remove depKey from schema.dependencies (and delete schema.dependencies if empty); if depVal is a string array, when depKey in cleanData, add non-excluded strings in depVal to schema.required; if depVal is a JsonObject, when depKey in cleanData, resolve depVal and merge matching branches into schema while excluding depKey (unless depKey is in ownKeys) and previousStepKeys.
8. 8. When evaluating oneOf or anyOf branches (inside dependencies or at step root), build each branch's condition test schema from its discriminator properties (properties equal to depKey, in previousStepKeys, not in ownKeys with const/enum, or having const/enum without field type/title) and require those discriminator keys in the condition test schema if they have const or enum so newly introduced required step fields in branch.required do not prevent the branch from matching before the user fills them in.
9. 9. When merging a resolved branch into target schema, recursively resolve nested conditionals on the branch first, merge branch.properties entries into target.properties while skipping excluded keys and pure discriminator constraint definitions (objects having const or enum without type, title, properties, items, ui:field, or ui:widget), and merge branch.required strings into target.required (deduplicated) only for non-excluded keys.
10. 10. If schema.properties contains nested type: 'object' property schemas and options?.resolveAll is true, recursively resolve each nested object property schema against cleanData[propKey] (when cleanData[propKey] is a JsonObject) so nested conditional properties are also resolved.

Exports:
