# Intent Brief — feature-new — Entity former names and rename redirects

## Context

A catalog entity's URL is built from its kind, namespace and name, so renaming a service (or moving it to another namespace) breaks every bookmark, wiki link and chat message that pointed at it, and the user just sees "Entity not found". Other plugins that key on the entity name, such as TechDocs URLs, break the same way. The request has been open since 2021 (backstage/backstage#5231).

Discovery found no existing rename, alias or former-name concept in the codebase. The closest pattern is TechDocs' `backstage.io/techdocs-entity` external redirect (`useExternalRedirect` + `TechDocsRedirectNotification`).

Seed (user's words): "Remember an entity's former names in the Backstage catalog and redirect old entity-page and TechDocs links to the renamed entity, with a notice."

## Goal

- **Before:** opening an old link such as `/catalog/default/component/old-name` shows the "Entity not found" page.
- **After:** the same link lands on `/catalog/default/component/new-name` with a notice that the entity was renamed from `old-name`. TechDocs links (`/docs/default/component/old-name/...`) redirect the same way.

Where the work lands:

- `packages/catalog-model`: a way to declare former names, for example an annotation.
- `plugins/catalog-backend`: index former refs, resolve them in lookups without letting one entity hijack another's name, and handle conflicts.
- `packages/catalog-client`: a lookup method.
- `plugins/catalog` and `plugins/techdocs`: redirect from the not-found path, with a "this entity was renamed" notice.

The architecture phase must answer these design questions:

1. Who may claim a former name?
2. What happens when a new entity takes an old name? A live entity with the exact ref must always win.
3. How is the redirect target permission-checked? The caller must have read access to the target, and an entity the caller can't see must not leak.
4. How do existing lookups stay fast? Fall back only after a miss, and index the former refs.

## Acceptance criteria

1. An entity can declare its former names in its descriptor; the declaration is documented in the well-known annotations page.
2. The backend indexes former refs and resolves an unknown ref to the renamed entity, with:
   - a live entity that has the exact ref always winning over a former-name claim;
   - a defined, tested outcome when more than one entity claims the same former name (no hijacking);
   - the redirect target subject to the same read permission as a direct lookup (no leak of entities the caller can't read);
   - no extra query cost on lookups that hit directly.
3. The catalog client exposes the lookup, and the OpenAPI spec and generated code agree with it.
4. Opening `/catalog/<ns>/<kind>/<old-name>` navigates (replace) to the new entity's page and shows a "renamed from old-name" notice, in both the legacy and new frontend systems.
5. Opening a TechDocs URL for the old name navigates to the new entity's docs, keeping the sub-path, with the same kind of notice.
6. Tests:
   - backend unit tests for former-name indexing, conflict handling and permissioned lookup;
   - jsdom tests for the redirect and notice on the entity route and the docs route.
7. `yarn tsc` and `yarn lint` pass, the API reports are regenerated, and changesets cover every changed published package.

## Non-goals

- Detecting renames automatically from location or processing history without a declaration.
- Redirecting other plugins' entity-keyed routes beyond the catalog entity page and TechDocs.
- Rewriting existing relations or references that point at old refs.
- Migrating or republishing TechDocs storage under the new name.
- Changes to `techdocs-backend` routes (the frontend redirect resolves before the backend calls).
