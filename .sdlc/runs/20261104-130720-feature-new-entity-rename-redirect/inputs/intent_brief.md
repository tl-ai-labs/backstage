## Brief (verbatim)

Problem: A catalog entity's URL is built from its kind, namespace and name, so renaming a service (or moving it to another namespace) breaks every bookmark, wiki link and chat message that pointed at it, and the user just sees "Entity not found". Other plugins that key on the entity name, such as TechDocs URLs, break the same way. Request open since 2021 (backstage/backstage#5231).

Before: opening an old link such as /catalog/default/component/old-name shows the "Entity not found" page.
After: the same link lands on /catalog/default/component/new-name with a notice that the entity was renamed from old-name.

Where the work lands: packages/catalog-model (a way to declare former names, for example an annotation), plugins/catalog-backend (index former refs, resolve them in lookups without letting one entity hijack another's name, and handle conflicts), packages/catalog-client (lookup method), and plugins/catalog plus plugins/techdocs (redirect from the not-found path with a "this entity was renamed" notice).

Design questions to answer: who may claim a former name, what happens when a new entity takes an old name, permission checks on the redirect target, and keeping existing lookups fast.

Acceptance criteria: backend tests for former-name indexing, conflict handling and permissioned lookup; jsdom tests for the redirect and notice on the entity and docs routes; yarn tsc and lint pass.

Tests: unit tests in the backend plus jsdom tests in the frontend plugins.

## Context

- Entity pages resolve `/catalog/:namespace/:kind/:name` through
  `plugins/catalog/src/components/CatalogEntityPage/useEntityFromUrl.ts`, which calls
  `catalogApi.getEntityByRef`; a miss renders the "Entity not found" warning panel from `EntityLayout`
  (old frontend system) or `EntityLayoutBui` (new frontend system, `plugins/catalog/src/alpha/`).
- The catalog backend serves `GET /entities/by-name/:kind/:namespace/:name` from
  `plugins/catalog-backend/src/service/createRouter.ts`, typed from `src/schema/openapi.yaml`; reads go
  through `DefaultEntitiesCatalog` wrapped by `AuthorizedEntitiesCatalog` for permissions. Knex
  migrations live in `plugins/catalog-backend/migrations/` (latest `20261007000000`).
- `@backstage/catalog-client`'s `CatalogApi` has three implementers in the repo: `CatalogClient`,
  `InMemoryCatalogClient` (testUtils, also behind catalog-react's `catalogApiMock`), and catalog-node's
  `DefaultCatalogService`, which implements the separate `CatalogService` interface.
- TechDocs shows its not-found page from `TechDocsReaderPageContent` / `TechDocsNotFound`; a redirect
  notice component already exists at `plugins/techdocs/src/reader/components/TechDocsRedirectNotification/`.
- `plugins/catalog-backend/CLAUDE.md` asks that changes to catalog queries, indexes or schema keep the
  query battery's reference SQL (`src/tests/performance/query-battery/queries.md`) in step with any changed
  query shape.

## Goal

An entity can declare the names it was formerly known by. The catalog indexes those former refs and can
resolve an old ref to the current entity, without one entity taking over a name another entity holds, and
with conflicts handled. Opening an old entity-page link or TechDocs link lands on the renamed entity (or its
docs) with a notice that it was renamed from the old name. The design answers: who may claim a former name,
what happens when a new entity takes an old name, permission checks on the redirect target, and how existing
lookups stay fast.

## Acceptance criteria

1. An entity can declare its former names through `packages/catalog-model` (for example an annotation).
2. `plugins/catalog-backend` indexes former refs and resolves them in lookups; one entity cannot hijack a name
   another entity holds, and conflicts between claims are handled.
3. `packages/catalog-client` exposes a lookup method for resolving a former ref.
4. Opening an old link such as `/catalog/default/component/old-name` lands on
   `/catalog/default/component/new-name` with a notice that the entity was renamed from `old-name`, instead of
   the "Entity not found" page.
5. An old TechDocs link for a renamed entity lands on the renamed entity's docs with the same kind of notice.
6. The design answers: who may claim a former name, what happens when a new entity takes an old name,
   permission checks on the redirect target, and keeping existing lookups fast.
7. Backend tests cover former-name indexing, conflict handling and permissioned lookup.
8. jsdom tests cover the redirect and notice on the entity route and the docs route.
9. `yarn tsc` and lint pass.
10. Repo companions: API and SQL reports regenerated, changesets for every published package changed, docs
    updated for the new declaration and lookup.

Test command (the study's fixed command for BS-NF-12, used word for word by every policy's run):
`CI=true yarn test plugins/catalog-backend plugins/catalog plugins/techdocs && yarn tsc && yarn lint:all`

Run settings confirmed at Gate 0: auth mode `vendor`; policy `argon4-agsdk-only`; no `.gitignore` change.

## Non-goals

- Changes to packages the brief does not name, beyond the companion files listed above.
- Running the catalog query battery against a database replica: it needs connection details from the user.
  The design still has to argue how existing lookups stay fast.
