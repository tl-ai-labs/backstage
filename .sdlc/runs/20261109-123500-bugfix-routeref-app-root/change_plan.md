## Decisions

- Public API addition for re-resolution: Add two optional methods to the public `RouteResolutionApi` interface in frontend-plugin-api: `subscribe?(listener: () => void): () => void` (listener is called when route resolution changes; returns an unsubscribe function) and `isPending?(): boolean` (true while only part of the app's routes are known, so a ref that does not resolve yet may resolve later). (not An Observable-returning `routeResolution$()` method, which needs an Observable implementation in frontend-app-api for a single void event; not Duck-typed private methods on the proxy (like the existing getRouteObjects), which core-plugin-api cannot rely on as a contract; not A single subscribe method without a pending signal, which cannot keep the legacy hook throwing for unresolvable refs after finalization (FR-5)) — Optional members keep every existing custom RouteResolutionApi implementation compiling (FR-6), and the legacy hook needs a synchronous pending signal at render time.
- How hooks re-resolve: Each useRouteRef keeps `const [revision, setRevision] = useState(0)`, subscribes in a `useEffect` keyed on the API instance with a listener `() => setRevision(r => r + 1)` (returning the unsubscribe function, or undefined when the API has no `subscribe`), and adds `revision` to the existing `useMemo` dependency array behind `// eslint-disable-next-line react-hooks/exhaustive-deps`. (not useSyncExternalStore (React 18 only, the packages also support React 17); not Re-resolving on every render (breaks the existing tests that count resolve calls and re-renders nothing on its own)) — A revision bump re-renders a consumer exactly once per real route-resolution change and never otherwise (FR-3, FR-4).
- When the proxy notifies and what pending means: RouteResolutionApiProxy.initialize takes a third optional argument `options?: { pending?: boolean }`, stores `#pending = options?.pending ?? false`, replaces the delegate and route objects, then calls every listener synchronously, iterating over a copy of the listener set. instantiateAndInitializePhaseTree passes `{ pending: Boolean(options.stopAtAttachment) }`, so the bootstrap phase (the only caller that stops at the session boundary) is pending and every finalization is not. (not A new flag threaded from createBootstrapApp in treeLifecycle.tsx (one more file edited for the same information); not Notifying only when the route info differs (route info has no cheap equality; initialize runs once per phase)) — Route info is partial exactly when tree instantiation stopped at an attachment, and initialize runs once at bootstrap (no subscribers yet) and once at finalization.
- Legacy core-plugin-api useRouteRef while routes are pending: When backed by the new frontend system's RouteResolutionApi, a non-optional ref that resolves to undefined throws `No path for ...` only if `routeResolutionApi.isPending?.()` is not true; while pending it returns undefined and re-renders on the next notification. The public overload signatures are unchanged. (not Suspending (throwing a promise) until finalization, which hides the whole app behind the nearest Suspense for root elements without their own boundary, including the sign-in page; not Widening the overload return type to include undefined, which is a breaking type change for a 1.x package) — Root elements render during sign-in without crashing (FR-2) and finalized apps keep today's error for unresolvable refs (FR-5).
- RouteResolver.ts, treeLifecycle.tsx, prepareSpecializedApp.tsx, createSpecializedApp.tsx, extractRouteInfoFromAppNode.ts: Left unchanged. — RouteResolver.resolve already returns undefined when the target ref has no known path (resolveTargetRef), and its `No path for` throw at line 153 only fires for a known target whose parent has no path, which partial bootstrap info does not produce; both phases already call initialize through instantiateAndInitializePhaseTree.
- Changesets: Two new files: .changeset/route-resolution-api-subscribe.md for '@backstage/frontend-plugin-api' (new optional API methods and useRouteRef updating), and .changeset/route-ref-before-app-finalized.md for '@backstage/frontend-app-api' and '@backstage/core-plugin-api' (components rendered before the app finishes loading no longer fail on useRouteRef and update afterwards); all patch. — Each changeset message must be relevant to every package it names; no existing changeset covers these packages.
